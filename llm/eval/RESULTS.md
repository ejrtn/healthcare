# 평가 결과 및 설계 결정

이 프로젝트의 RAG 파이프라인(청킹 → 병명/카테고리 라우팅 → 리랭킹 → 증상 기반 멀티턴
문진)을 만들면서 실제로 측정해서 내린 결정들을 정리한 문서. 재현 스크립트는
`run_eval.py`, `chunk_size_experiment.py`이고, 정답 라벨은 `ground_truth.py`에 있다.

## 전체 파이프라인 요약

```
XML(질병관리청 1,145개)
  → 정제(base64/HTML 제거) + 청킹(400자, 문장 단위, 60자 overlap)
  → 임베딩("병명 카테고리: 내용" 형태로 인코딩) → ChromaDB (29,214청크)

질문
  ├─ 병명 언급됨   → 병명+카테고리 메타데이터 필터 → 벡터검색(8) → 리랭킹 → top-3
  └─ 병명 미언급   → 전체 벡터검색(40) → 후보 병 개수로 분기
                      ├─ 10개 초과   → "너무 많음, 증상 더 알려달라" (LLM 호출 없음)
                      ├─ 3~10개     → 후보 목록 나열 + 추가 증상 요청 (LLM 호출 없음)
                      ├─ 3개 미만    → top-3로 리랭킹 → 답변 생성
                      └─ 되묻기 3회를 다 써도 안 좁혀짐 → 병명별 대표 청크 하나씩 모아
                         "총 N개 중 top-3는 ..."로 요약 (LLM 호출 없음)
  → THRESHOLD(0.5) 미달이면 → guess_standard_term()으로 LLM이 줄임말인지 추측 →
     맞으면 되묻기, 아니면 "관련 없음" 거절
  → llama-cpp-python(Llama-3.1-8B-Q4)으로 답변 생성 + 출처 표시
```

## 정답 라벨셋

- **카테고리 라우팅**: 12개 병명(고혈압/당뇨병/감기/간흡충증/골다공증/빈혈/편두통/
  대상포진/아토피피부염/갑상선기능항진증/중이염 등) × 원인/증상/진단/약물/치료/예방/
  합병증/생활관리 33문항. 카테고리 이름이 병마다 다르고 의미가 겹치는 카테고리(예:
  "생활습관 관리" ≈ "자가 관리", "원인" ≈ "병태생리")가 있어서 `expected`를 리스트로
  두고 그중 하나만 맞아도 정답으로 채점한다.
- **거절(reject)**: 데이터베이스에 없는 질문 9개 — 날씨/주식/코드작성/산수/
  랜덤문자열 등 의료와 아예 무관한 5개, 그리고 실제 병명이지만 이 데이터셋에는
  없는 4개(위염/불면증/몸살/위궤양). "관련 없음"으로 정직하게 답해야 한다
  (THRESHOLD 게이트 검증).
- **증상 기반**: 병명 없이 증상만 설명하는 질문 23개 — 최초 6개, 다른 신체
  부위/증상 계열로 확장한 10개(어지럼, 요통, 설사, 결막염, 무좀, 비염, 방광염,
  우울감, 족저근막염, 알레르기 계열), 그리고 구어체·모호한 표현·부정문을 일부러
  어렵게 낸 7개(아래 참고). 의사가 아니라서 "이 증상=이 병"으로 확정할 수
  없으므로, 실제로 병원에서 감별진단하는 대표 후보군을 `acceptable_diseases`로
  넉넉히 잡고 그중 하나만 최상위로 나와도 정답으로 채점한다. 후보 병명은 전부
  `data/medical_knowledge.jsonl`에 실제로 등록된 `disease` 값과 정확히
  일치하는지 확인하고 넣었다(등록 안 된 이름을 넣으면 항상 채점에서 떨어지는
  거짓 실패가 생기기 때문).

## 실험 1: 청크 크기 (100 ~ 600자)

100자부터 600자까지 100자 단위로 다시 청킹하고, 리랭킹 없이 벡터 검색 1등이 정답
카테고리와 일치하는지 채점했다.

| 청크 크기 | 정확도 | 청크 수(6개 병 기준) |
|---|---|---|
| 100자 | 11/12 | 1,480 |
| 200자 | 11/12 | 653 |
| **300자** | **12/12** | 387 |
| **400자 (채택)** | **12/12** | 296 |
| **500자** | **12/12** | 241 |
| 600자 | 11/12 | 211 |

300~500자가 sweet spot이고 400자(채택값)가 그 한가운데다. 100자는 너무 잘게
쪼개져서 하나로 이어지던 정보(당뇨병 약물 설명 등)의 문맥이 흐려지고, 600자는
반대로 여러 주제가 한 청크에 섞여 벡터가 흐려진다.

## 실험 2: 카테고리 라우팅 정확도 (33문항, 최신)

| | 정확도 |
|---|---|
| RAW (리랭킹 없음) | 30/33 (90.9%) |
| **FINAL (리랭킹 적용)** | **31/33 (93.9%)** |

문항을 12개→33개로 늘리고 나서는 **리랭킹이 순정확도를 개선**했다 (처음 12문항
테스트에서는 리랭킹이 오히려 정확도를 낮추는 것처럼 보였는데, 표본이 작아서 생긴
착시였다 — 표본을 늘려 결론이 뒤집힌 경우라 그대로 기록해둔다).

유일하게 리랭킹이 정답을 틀리게 만든 문항은 "당뇨병 무슨 약 먹어?"로, RAW는
"치료"(정답)를 맞췄는데 리랭킹이 "합병증"으로 밀어냈다 (리랭커 점수 0.3631 vs
0.3847로 둘 다 낮고 근소한 차이 — 리랭커도 확신이 없는 상태에서 뒤집은 것). 다만
최종 답변 단계에서 top-1이 아니라 top-3를 통째로 LLM에 넘기기 때문에, 실제
`/chat`으로 확인한 결과 정답 카테고리(치료 안의 메트포민 정보)가 여전히 컨텍스트에
포함되어 최종 답변 자체는 정확했다.

## 실험 3: 거절(reject) 정확도 — THRESHOLD 튜닝

처음 THRESHOLD=0.7로 거절 테스트를 돌렸더니 **0/5로 완전히 실패**했다. 날씨/주식/
코드요청/산수/랜덤문자열 같은 완전히 무관한 질문도 거리 0.54~0.61 사이로 나와서
0.7 밑이라 답을 만들려고 시도했다 (의료 챗봇에서 가장 위험한 실패 유형).

관련 있는 질문과 무관한 질문의 거리 분포를 직접 비교해봤다:

| | 거리 |
|---|---|
| 관련 있는 질문 중 최대 | 0.589 ("간흡충증 치료법은?") |
| 무관한 질문 중 최소 | 0.541 ("오늘 날씨 어때?") |

두 분포가 겹쳐서 완벽하게 분리되는 임계값은 없다. **THRESHOLD를 0.5로 낮춰서**
거절 테스트를 5/5(100%)로 고쳤고, 그 대가로 "간흡충증 치료법은?"(거리 0.589) 하나가
덩달아 거절된다 (33문항 중 1개 희생 — 의료 챗봇은 무관한 질문에 답을 지어내는
것보다 애매한 경우 거절하는 쪽이 안전하다고 판단해 이 트레이드오프를 받아들였다).

**거절 케이스 확장(4문항 추가) — 실측 결과: 5/9 (55.6%)**: 위 5문항(날씨/주식/
코드/산수/랜덤문자열)은 의료와 아예 무관해서 임베딩 거리가 멀기 때문에 거절이
상대적으로 쉬운 케이스다. 더 어려운 시험을 위해 **실제로 존재하는 병명이지만
이 데이터셋(707개)에는 없는** 질문 4개(위염, 불면증, 몸살, 위궤양 —
`data/medical_knowledge.jsonl`의 disease 필드에 없음을 직접 확인)를 추가했는데,
**4개 전부 거절에 실패했다**:

| 질문 | 거리 | 결과 |
|---|---|---|
| 위염은 어떻게 치료해? | 0.278 | FAIL(답을 만들려 함) |
| 위궤양 증상이 뭐야? | 0.293 | FAIL(답을 만들려 함) |
| 몸살 나면 어떻게 해야 해? | 0.371 | FAIL(답을 만들려 함) |
| 불면증 원인이 뭐야? | 0.425 | FAIL(답을 만들려 함) |

이 4문항의 거리(0.278~0.425)는 기존 5문항의 거리(0.541~0.611)보다 훨씬 가깝다 —
예상대로 의료 도메인 안에 있는 질문이라 임베딩이 "관련 있어 보이는" 콘텐츠를
찾아버렸다. 이건 THRESHOLD=0.5 하나만으로는 **"완전히 무관한 질문"은 잘
걸러내지만 "이 데이터셋에 없는 병명"은 못 걸러낸다**는, 코사인 거리 기반 거절
게이트의 실제 한계를 보여준다. `detect_diseases()`가 정확히 일치하는 병명만
인식하기 때문에 애초에 병명으로 감지되지도 않고(감지병명=[]), 전체 벡터 검색이
"그나마 가장 가까운" 무관한 콘텐츠를 답으로 만들어버리는 구조적 문제다 —
개선하려면 THRESHOLD를 더 낮추는 것만으로는 부족하고, "검색된 병명이 사용자가
물어본 병명과 실제로 일치하는가"를 한 번 더 확인하는 별도 검증 단계가
필요해 보인다.

## 실험 4: 증상 기반 감별진단 (최초 6문항)

| | 정확도 |
|---|---|
| 증상 → 후보 병명 매칭 | 4/6 (66.7%) |

성공 사례: "배가 아프고 열이 나요"→복통, "머리가 지끈지끈"→두통,
"두드러기+가려움"→두드러기 등. 실패 사례 2건은 검토 결과 실제 데이터 한계로
남겨둔다: "기침+목아픔"이 "성대결절"로, "귀아픔+난청"이 "이명"으로 나오는데, 아예
무관하진 않지만 원래 기대했던 편도염/중이염만큼 정확한 매칭은 아니다.

**커버리지 확장 1차(10문항) — 실측 결과: 7/10 (70%)**: 위 6문항은 전부
소화기/호흡기/피부 계열에 쏠려 있어서, 신체 부위·증상 계열을 넓히려고
어지럼(전정계), 요통(근골격계), 설사(소화기), 결막염(안과), 무좀(피부),
비염(호흡기), 방광염(비뇨기), 우울감(정신건강), 족저근막염(근골격계),
알레르기 복합 증상 10문항을 `ground_truth.py`에 추가했다. "그럴듯하면 통과"
하도록 acceptable_diseases를 넉넉히 잡아뒀는데도 3건이 실패했다 — 그냥 실패가
아니라 **다른 병의 존재를 몰랐다면 그럴듯해 보였을 오답**이라 흥미롭다:

| 질문 | 기대 후보 | 실제 결과 | 거리 |
|---|---|---|---|
| 허리가 계속 아파요 | 요통 | **강직성척추염** / 증상 | 0.306 |
| 배가 사르르 아프면서 묽은 변을 자주 봐요 | 설사/과민성 장증후군 등 | **변실금** / 종류 | 0.354 |
| 눈이 가렵고 충혈됐어요 | 알레르기결막염 등 | **안외상(각막찰과상)** / 증상 | 0.313 |

세 건 다 "요통"·"설사"·"알레르기결막염" 같은 흔한 병명이 데이터셋에 분명히
있는데도, 임베딩이 그보다 **덜 흔하지만 증상 묘사가 우연히 더 비슷한 다른
병**("강직성척추염", "변실금", "안외상")의 "증상" 카테고리 청크를 더 가깝다고
판단해버렸다. 의료 챗봇 입장에서는 이게 THRESHOLD로 걸러지는 "모르겠다"보다
더 위험할 수 있다 — 확신 있게(THRESHOLD 통과) 그럴듯한 오답을 내놓기 때문이다.

**커버리지 확장 2차(7문항) — 실측 결과: 2/7 (28.6%), 일부러 어렵게 낸 문항**:
신체 부위가 아니라 **표현 방식**의 다양성을 테스트하는 문항을 추가했는데,
여기서는 방향을 바꿨다. 1차 확장은 "그럴듯하면 통과"하도록 넉넉하게 설계했지만,
2차는 반대로 **임베딩 검색이 실제로 흔들릴 만한 지점을 일부러 찾아서** 넣었다
— 예상대로 대부분 실패했고, 그건 테스트가 잘못된 게 아니라 그 지점의 한계가
드러난 것으로 읽어야 한다.

| 질문 | 기대 후보 | 실제 결과 | 판정 |
|---|---|---|---|
| 삭신이 다 쑤셔요 | 섬유근육통/감기/만성피로증후군 | 구역질과 구토 / 정의 (거리 0.434) | FAIL |
| 속이 니글거려요 | 구역질과 구토/소화불량 | **위식도역류질환** / 증상 (거리 0.465) | FAIL |
| 머리가 띵해요 | 두통/편두통/어지럼 등 | 관련없음으로 거절됨 | FAIL |
| 몸이 좀 안 좋아요 | 감기/만성피로증후군 | **기후변화에 의한 폭염 예방 및 대처** (거리 0.378) | FAIL |
| 요즘 계속 피곤하고 잠도 잘 안 와요 | 만성피로증후군 | 만성피로증후군 / 증상 (거리 0.352) | **OK** |
| 화장실을 자주 안 가는데 배가 콕콕 찌르듯 아파요 | 담석증/과민성 장증후군 등 | **직장탈출증** / 종류 (거리 0.393) | FAIL |
| 울긋불긋 뭐가 올라오는데 가렵지는 않아요 | 두드러기 | 두드러기 / 종류 (거리 0.416) | **OK** |

몇 가지 짚을 점:
- **"몸이 좀 안 좋아요" → "기후변화에 의한 폭염 예방 및 대처"**는 설계할 때
  예상했던 "정답이 궁색한 케이스"가 실제로 어떤 식으로 실패하는지 정확히
  보여주는 사례다 — 신체 부위·증상이 전혀 없는 질문에 임베딩이 그나마
  가까운(하지만 완전히 무관한) 건강 정보를 억지로 갖다 붙인 것.
- **"머리가 띵해요"는 다른 FAIL들과 성격이 다르다** — 답을 잘못 낸 게 아니라
  THRESHOLD를 넘겨서 **정직하게 거절됐다**. 이 테스트의 채점 기준상 거절도
  FAIL로 집계되지만, 의료 챗봇 관점에서는 모호한 질문에 그럴듯한 오답을
  내는 것보다 거절하는 쪽이 훨씬 안전한 행동이다 — 즉 이 FAIL은 "나쁜 실패"가
  아니라 "안전한 실패"다.
- **"속이 니글거려요" → "위식도역류질환"**은 뜻밖의 발견이다. 실험 3에서
  "역류성"이라는 문자열로는 데이터셋에 없는 걸 확인했었는데, 실제로는
  "위식도역류질환"(역류성 문자열 없이 다른 이름)이라는 이름으로 등록돼 있었다
  — 이름 검색만으로 데이터셋 커버리지를 판단하면 놓칠 수 있다는 방법론적
  교훈.

**증상 기반 22문항 확장분 종합**: 최초 6문항(4/6) + 1차 확장 10문항(7/10) +
2차 확장 7문항(2/7) = **13/23 (56.5%)**. 2차 확장이 일부러 정확도를 끌어내리도록
설계된 만큼, 전체 정확도가 66.7%(최초 6문항)보다 낮게 나온 것 자체가 테스트가
의도대로 작동했다는 신호다.

### 발견: 안내문이 병명 목록에 섞여 들어간 데이터 결함

"몸이 춥고 그런데"처럼 아주 일반적인 증상 질문을 테스트하다가, 후보로 **"겨울철
한파대비 건강수칙", "겨울철 대설대비 건강수칙"** 같은 실제 질병이 아닌 정부
공공안내문이 뽑히는 걸 발견했다. 이게 섞여 있으니 후속 질문 생성 로직이 "이 두
안내문의 차이가 뭔가요?" 같은 말도 안 되는 질문을 만들어냈다.

`diseases.json` 707개 중 "수칙/요령/대비"가 제목에 들어간 5개 항목을 찾아서
`parse_xml.py`에서 원천 필터링했고 (해당 질환의 실제 정보는 "동상", "저체온증" 등
별도 항목으로 이미 있어서 정보 손실 없음), 라이브 벡터DB에서도 49개 청크를 직접
삭제해 반영했다. 재발 방지를 위해 `NON_DISEASE_SUBJECT_PATTERNS`로 파싱 단계에서
계속 걸러진다.

## 기능: 증상 기반 멀티턴 문진 + 진료과 추천

병명 없이 증상만 말하는 질문에 대해, 사용자가 대화하듯 증상을 추가해가며 후보를
좁힐 수 있게 만들었다.

- **후보 규모에 따라 3단계로 응답**: 후보 병명이 10개 넘으면 목록 없이 "질병이 너무
  많으니 증상을 더 알려달라"고만 답하고, 3~10개면 후보 목록을 그대로 보여주며 추가
  증상을 요청하고, 3개 미만이면 구체적인 답변(질환 추정 + 진료과 추천)을 준다. 전부
  결정론적 규칙이라 LLM 호출이 없어 빠르고, 안내문처럼 후보 이름 자체가 이상해서
  생기던 이상한 되묻기 질문 문제도 같이 사라졌다.
- **대화 이력 누적**: 프론트엔드가 매 요청마다 지금까지의 대화를 통째로 보내고,
  서버는 사용자 발화를 다 이어붙여 누적 증상 질의로 검색한다 (서버는 상태를 안 가짐).
- **되묻기 상한(3회)**: 그래도 안 좁혀지면 후보 병명별로 대표 청크를 하나씩 모아
  "~등 여러 질환이 예상됩니다"처럼 하나로 확정하지 않는 답변으로 마무리한다.
- **진료과 추천 어투**: "~에서 진료를 받을 수 있습니다"처럼 사실을 서술하지 않고
  "~과 방문을 권장드립니다"처럼 추천 어투로, 질환도 "~이 의심됩니다"처럼 추정
  표현으로 안내하도록 프롬프트에 명시했다. (진료과 매핑 데이터가 따로 없어서 LLM의
  일반 지식에 의존한다 — 아래 한계점 참고.)

## 실험 5: RAGAS 생성 품질 평가 (`ragas_eval.py`)

실험 1~4(위)는 전부 **검색이 맞는 걸 찾아오는가**(카테고리 라우팅, 거절, 증상
매칭)를 채점한다. 여기서는 한 걸음 더 나아가 **실제로 생성된 답변**이 근거
있게 작성됐는지(faithfulness)와 질문에 맞게 작성됐는지(answer_relevancy)를
LLM judge로 채점한다 — 채용 공고 리서치에서 "RAG 정량 평가 경험"이 반복적으로
요구돼서 도입했다.

### judge를 외부 API 대신 로컬 Llama로 고정한 이유

RAGAS의 `Faithfulness`/`ResponseRelevancy`는 LLM judge가 필요하다(답변을 주장
단위로 쪼개서 각각 컨텍스트와 대조하는 식이라, 질문 1개당 judge 호출이 여러
번 발생). 대부분의 RAGAS 사용 사례는 GPT-4급 API를 judge로 쓰는데, 이 프로젝트는
"100% 로컬, 외부 API 호출 없음"이 핵심 설계 철학이라(README 참고), 평가 도구에서만
그 원칙을 깨고 싶지 않아 **judge도 이미 main.py가 로드해둔 로컬
Llama-3.1-8B-Q4를 그대로 재사용**했다. 트레이드오프는 솔직히 있다: 8B급 로컬
모델은 GPT-4급보다 판정이 불안정할 수 있고, CPU 추론이라 문항당 judge 호출이
여러 번 겹치면 33문항 전체를 돌리는 데 상당히 오래 걸린다(참고: 답변 1개
생성에도 수십 초). 그래서 기본 실행은 일부 문항만 샘플링하고 `--full`로 전체를
돌릴 수 있게 했다.

### 구현 메모 (ragas==0.4.3 기준)

- **상위 버그 회피**: `pip install ragas`만 하면 langchain-community 최신판이
  같이 깔리는데, `ragas.llms.base`가 무조건
  `from langchain_community.chat_models.vertexai import ChatVertexAI`를
  import해서 — 그 서브모듈이 langchain-community 0.4대에서 이미 삭제(sunset)돼
  `import ragas` 자체가 즉시 깨진다. `eval/requirements-ragas.txt`로
  langchain 계열을 전부 0.3대로 고정해서 우회했다.
- **구(舊) 메트릭 API를 의도적으로 선택**: ragas 0.4.3의 "최신"
  `ragas.metrics.collections.Faithfulness`는 `instructor` 라이브러리의
  tool-calling 기반 구조화 출력을 강제한다 — 로컬 8B Q4 양자화 모델에게 이걸
  안정적으로 시키기는 어렵다고 판단해서, 대신 순수 텍스트 생성 + JSON 파싱
  방식인 구 `ragas.metrics.Faithfulness`/`ResponseRelevancy`
  (`PydanticPrompt.generate` 사용, deprecated 경고는 뜨지만 이 버전에서 정상
  동작)를 그대로 썼다.
- **모델 이중 로드 회피**: judge/임베딩을 새로 로드하는 대신 main.py가 이미
  로드한 `llm`(llama-cpp-python)과 `embed_model`(ko-sroberta-multitask)을
  각각 langchain `LLM`/`Embeddings` 서브클래스로 얇게 감싸서 재사용했다 — 안
  그러면 8B GGUF를 서빙용과 평가용으로 메모리에 두 번 올리게 된다.

### 현재 상태 — 실제 8B로 실행, 로컬 judge의 실제 한계에 부딪힘

`mock`으로 배관만 검증했던 이전 상태에서 나아가, 실제 런타임 의존성이 설치된
환경에서 `python eval/ragas_eval.py --full`(33문항)을 실제로 돌려봤다.
33문항 중 14문항까지는 정상적으로 채점됐다(faithfulness 평균 0.91, answer
relevancy 평균 0.59 수준 — 예비 수치, 아래 크래시 이후 재실행 전까지는
잠정치). 그런데 15번째 문항(`간흡충증 치료법은?`)은 THRESHOLD 미달로 정상
제외됐고, 그다음 문항에서 **로컬 8B judge가 같은 문장을 수십 번 반복하는
디제너레이션(생성 퇴화)에 빠졌다** — RAGAS가 "출력 형식이 틀렸다"며
재프롬프트하는 과정에서 망가진 이전 출력 + 재시도 지시문이 계속 쌓여
`n_ctx=4096`(main.py 설정)을 넘겨버려 `ValueError: Requested tokens (4686)
exceed context window of 4096`으로 스크립트 전체가 죽었다.

이건 정확히 이 문서 위쪽에서 우려했던 "8B급 로컬 모델은 GPT-4급보다 판정이
불안정할 수 있다"는 트레이드오프가 실제로 발생한 사례다 — 로컬 judge를
선택한 것에 따르는 진짜 비용을 실측으로 확인한 셈이다. 게다가 원래 코드는
결과를 루프가 다 끝난 뒤 한 번에 저장하는 구조라서, 크래시 시점에 **이미
정상 채점된 14문항 결과가 통째로 유실**되는 2차 문제까지 있었다.

**적용한 수정**:
- `LocalLlamaJudge._call`에 `repeat_penalty=1.3` 추가(반복 억제)하고
  judge용 `max_tokens`를 1024→512로 낮춰 한 번의 디제너레이션이 컨텍스트를
  다 잡아먹기 전에 끊기게 했다. 컨텍스트 초과 `ValueError`는 잡아서 빈
  문자열을 반환하도록 해서, RAGAS 자체의 파싱 실패 재시도 로직으로만
  처리되게 하고 우리 쪽에서 예외를 다시 던지지 않는다.
- `run()` 루프에서 문항 하나가 judge 실패로 끝내 죽어도(RAGAS 자체 재시도
  소진 후) 그 문항만 건너뛰고 나머지를 계속 진행하도록 `try/except` 추가.
- 매 문항 채점 직후 결과 JSON을 즉시 덮어써서 저장(`save_progress()`)하도록
  바꿔서, 중간에 어떤 이유로든 죽어도 그때까지의 결과는 남게 했다.

### 완주 결과 (로컬 judge, 32문항)

위 수정을 반영해 `--full`을 다시 돌린 결과, 이번에는 **크래시 없이 32문항
(33문항 중 1건은 THRESHOLD 미달로 정상 제외) 전부 끝까지 처리됐다.**

| | 값 |
|---|---|
| 시도한 문항 | 32 |
| **파싱 성공(점수 확보)** | **13/32 (40.6%)** |
| 평균 faithfulness | 0.717 |
| 평균 answer_relevancy | 0.254 |

**파싱 성공률 자체가 실측 지표다**: 나머지 19문항은 `RagasOutputParserException`
(형식 재시도 소진), `TypeError: TextEncodeInput`(judge가 만든 역질문이
비정상적이라 임베딩 단계에서 깨짐), 컨텍스트 윈도우 초과 등으로 채점이
불가능했다 — 전부 이 문서 위쪽에서 예상했던 "로컬 8B judge는 GPT-4급보다
판정이 불안정하다"는 트레이드오프가 그대로 수치로 드러난 것이다. 40.6%라는
낮은 성공률 자체가 "로컬 judge 단독으로는 신뢰도 있는 평가 도구가 되기
어렵다 → 그래서 멀티 judge 교차 검증이 필요하다"는 이 프로젝트의 설계
근거를 실측으로 뒷받침한다.

**Gemini/ChatGPT는 이번엔 다른 이유로 건너뛰었다**: Gemini는
`RESOURCE_EXHAUSTED`(무료 선불 크레딧 소진), ChatGPT는
`insufficient_quota`(크레딧 없음) — 둘 다 코드 문제가 아니라 계정 상태
문제다. Claude는 크레딧을 유지하지 않기로 하면서 judge 목록에서 아예
제외했다(위 "멀티 judge" 절 참고). 무료 크레딧이 남은 계정으로 다시
돌리면 실제 멀티 judge 비교치를 얻을 수 있다 — 그 전까지는 로컬 judge
단독 실측치가 이 실험의 확정 결과다.

### 멀티 judge — 로컬 judge의 신뢰도를 다른 judge와 교차 검증

위 크래시로 "로컬 8B가 judge로서 불안정할 수 있다"는 우려가 실측으로
확인되자, 자연스러운 다음 질문은 "그럼 다른 judge와 비교하면 얼마나 다른가"
였다. 그래서 `ragas_eval.py`가 **judge를 하나가 아니라 최대 3개(로컬 +
Gemini + ChatGPT)까지 동시에 시도**하도록 확장했다. (Claude는 API 크레딧을
쓰지 않기로 하면서 제외했다 — 무료로 계속 유지 가능한 조합만 남겼다.)

- **"100% 로컬" 철학과 충돌하지 않는 이유**: 로컬 judge는 항상 무조건
  포함되고, 외부 API 키가 하나도 없어도 스크립트는 정상 동작한다(로컬만
  돌아감). 나머지 2개는 해당 API 키 환경변수(`GEMINI_API_KEY`,
  `CHATGPT_API_KEY` — 회사명이 아니라 서비스 이름으로 통일)가 있을 때만
  "추가로" 시도되는 선택적 교차 검증이다 — 프로덕션(`main.py`,
  `mcp_server.py`)은 여전히 외부 API를 전혀 안 쓴다. 이건 어디까지나
  "평가 도구가 스스로를 얼마나 믿을 수 있는지"를 검증하는 메타 실험이다.
- **연결 실패는 그 judge만 건너뛴다**: 각 judge를 실제로 쓰기 전에 짧은
  연결 테스트(`_smoke_test`)를 한 번 해보고, 키가 없거나 인증에 실패하거나
  SDK가 안 깔려 있으면 그 judge만 건너뛰고 나머지로 계속 진행한다 — 3개 중
  몇 개가 비어 있어도 스크립트가 죽지 않는다.
- **답변은 judge와 무관하게 한 번만 생성**: 3개 judge가 서로 다른 답변을
  채점하면 "judge가 다르다"와 "답변이 다르다"는 두 변수가 섞여서 비교가
  무의미해진다. 그래서 로컬 8B가 만든 답변을 한 번만 생성해서 캐싱해두고,
  그 **같은 답변**을 3개 judge에게 똑같이 채점시킨다 — 순수하게 "judge
  선택이 채점 결과에 얼마나 영향을 주는가"만 분리해서 본다.
- **embedding은 judge와 무관하게 항상 로컬**: answer_relevancy는 임베딩
  유사도로 계산하는데, 이것마저 judge마다 다른 embedding을 쓰면 비교가
  또 오염된다. 그래서 embedding은 3개 judge 전부 동일하게
  ko-sroberta-multitask를 쓴다.
- **결과는 judge별로 따로 저장**: `eval/results/ragas_run_{judge}.json`
  (예: `ragas_run_local.json`, `ragas_run_gemini.json`)로 나눠 저장하고,
  실행 끝에 judge별 평균을 나란히 비교하는 요약을 출력한다.

이 기능도 mock(가짜 `google.genai` 클라이언트)으로 3개 judge 경로(로컬 항상
포함, 1개는 키가 있어서 성공, 1개는 키가 없어서 건너뜀)가 전부 의도대로
동작하는 것까지 확인했다 — 다만 실제 API 키로 진짜 Gemini/ChatGPT를 호출해서
로컬 judge와 점수를 비교해보는 건 아직이다.

## 어떻게 재현하나

```bash
cd project
python eval/run_eval.py               # 카테고리 라우팅 + 거절 + 증상 매칭 (main.py 전체 로드, 수십 초)
python eval/chunk_size_experiment.py   # 청크 크기 스윕 (몇 분 소요, XML 재파싱+임시 임베딩)
python eval/ragas_eval.py              # RAGAS 생성 품질 평가 (pip install -r eval/requirements-ragas.txt 먼저 필요, 오래 걸릴 수 있음)
                                        # 기본은 로컬+사용 가능한 API judge 전부 시도. --judges local 로 로컬만,
                                        # llm/.env에 GEMINI_API_KEY/CHATGPT_API_KEY 채우면 그 judge들도 추가
```

`run_eval.py`/`ragas_eval.py`는 결과를 `eval/results/*.json`에 저장한다.
`chunk_size_experiment.py`는 `eval/.tmp/`에 임시 청킹 데이터와 임시 ChromaDB를
만들었다가 끝나면 지우며, 실제 프로젝트의 `data/medical_knowledge.jsonl`,
`vector_db/`는 건드리지 않는다.

## 알려진 한계

- **데이터셋에 없는 병명을 거절 못 함**: THRESHOLD(0.5)는 완전히 무관한
  질문(날씨/주식 등)은 잘 걸러내지만, "위염"/"불면증"/"몸살"/"위궤양"처럼
  의료 도메인 안에 있지만 이 KDCA 데이터셋(707개)엔 없는 병명은 거리가
  0.278~0.425로 가까워서 걸러내지 못한다(실측 4/4 전부 실패, 실험 3 참고).
  코사인 거리 하나로는 "무관함"과 "데이터셋에 없음"을 구분하지 못한다는
  구조적 한계.
- **그럴듯한 오답 생성**: 증상 기반 질문에서 정답 병명이 데이터셋에 있는데도
  임베딩이 증상 묘사가 우연히 더 비슷한 다른(더 드문) 병으로 잘못 수렴하는
  경우가 있다(예: "허리가 계속 아파요" → "요통" 대신 "강직성척추염", 실험 4
  참고). THRESHOLD를 통과하는 확신 있는 오답이라 거절보다 위험할 수 있다.
- **병명 축약형 미인식 → LLM 추측으로 완화**: "디스크"처럼 등록된 정식 명칭
  ("추간판탈출증(디스크)")의 일부만 말한 구어체는 규칙 기반 매칭·임베딩 검색
  둘 다 실패한다. THRESHOLD 미달로 완전히 거절하기 전에, `guess_standard_term()`으로
  LLM에게 이 표현이 어떤 질환의 줄임말인지 한 단어로 추측시켜서 맞으면 되묻는
  절충안을 추가했다(`main.py`). 여러 필드를 구조화해서 뽑아내는 에이전틱 실험과
  달리 "단어 하나 추측"이라는 단순 회상 작업이라 실패해도 원래 폴백으로
  안전하게 넘어간다 — 다만 이 기능 자체의 정확도는 아직 별도로 측정하지 않았다.
- **복합 의도 질문의 카테고리 분리**: "A의 원인, B의 치료법"처럼 병명별로 다른
  의도를 담은 한 문장은, 감지된 의도가 언급된 모든 병명에 공통 적용된다.
- **증상→병명 매칭 정밀도**: 상위 6문항 테스트에서 2건이 완전히 정확하진 않은
  질환으로 매칭됨 (성대결절, 이명) — 데이터셋 자체가 진료 지침용이지 감별진단용으로
  큐레이션된 게 아니라서 생기는 근본적 한계.
- **진료과 추천 신뢰도**: 데이터에 진료과 매핑이 없어 LLM의 일반 지식에 의존 —
  드물게 부정확하거나 애매한 과를 언급할 수 있음.
- **응답 속도**: CPU(llama-cpp-python, Q4 양자화)로 8B 모델을 돌려서 답변 생성에
  수십 초가 걸림. GPU가 있으면 `n_gpu_layers`를 올려서 크게 단축 가능.
