# 임베딩 모델 파인튜닝 결과

`eval/RESULTS.md`가 "이미 있는 모델을 어떻게 잘 조합해서 쓸까"(청킹/필터링/리랭킹)를
다뤘다면, 이 문서는 **모델 자체를 우리 데이터로 다시 학습시킨 결과**를 다룬다.

## 왜 임베딩 모델인가 (LLM이 아니라)

지식 자체는 벡터DB에만 있고 모델 가중치에는 없다 (RAG의 핵심 원칙). 그래서
파인튜닝도 "지식을 넣는" 게 아니라 **"검색 정확도를 높이는" 용도로만** 썼다.
8B LLM 파인튜닝은 GPU가 필요해 이 환경(CPU-only)에서 비효율적이지만, 임베딩
모델(`ko-sroberta-multitask`, 1.1억 파라미터)은 CPU로도 몇 분 안에 파인튜닝이
끝난다.

## 학습 데이터

`eval/ground_truth.py`의 33문항(질문, 병명, 기대 카테고리)에서 실제 청크 텍스트를
뽑아 (anchor=질문, positive=정답 카테고리 청크, negative=같은 병의 다른 카테고리
청크)로 변환했다. negative는 무작위가 아니라 **실제로 리랭킹 단계에서 헷갈렸던 것과
같은 종류의 하드 네거티브**(같은 병의 다른 카테고리)로 골랐다.

질문 단위로 섞어서 **train 25 / test 8**로 나눴다 (같은 질문이 양쪽에 안 걸치게).
test는 학습 때 모델이 전혀 보지 못한 데이터라, 여기서 좋아져야 "암기"가 아니라
"일반화"라고 말할 수 있다.

## 학습 방법

`sentence-transformers`의 `TripletLoss`로 4 epoch, batch size 4, CPU에서 79.7초
학습. `anchor`와 `positive`의 코사인 유사도는 높이고, `anchor`와 `negative`의
유사도는 낮추는 방향으로 가중치를 조정한다.

```bash
python finetune/build_training_data.py   # train.json / test.json 생성
python finetune/train_embedder.py        # ko-sroberta-finetuned/ 저장
python finetune/compare_embeddings.py    # 전/후 비교
```

## 결과: positive가 negative보다 실제로 더 유사하게 나오는 비율

측정 방법: 각 triplet에서 `cos_sim(anchor, positive) > cos_sim(anchor, negative)`인지
확인 — 이게 정확히 TripletLoss가 최적화하는 대상이라 가장 직접적인 지표다.

| | train (학습에 쓴 25개) | test (안 보여준 8개) |
|---|---|---|
| **파인튜닝 전** | 17/25 (68.0%), 평균 마진 0.034 | 5/8 (62.5%), 평균 마진 0.064 |
| **파인튜닝 후** | 25/25 (100%), 평균 마진 0.643 | **7/8 (87.5%)**, 평균 마진 0.273 |

(마진 = positive 유사도 − negative 유사도. 클수록 정답과 오답을 확실하게 구분한다는 뜻)

**train만 100%로 좋아졌다면 그냥 암기일 수 있는데, 한 번도 안 보여준 test에서도
정확도 62.5%→87.5%, 마진 0.064→0.273로 크게 개선됐다.** 이건 모델이 "이 25문항의
정답"을 외운 게 아니라, "우리 프로젝트에서 어떤 게 진짜 정답 카테고리인지 판단하는
일반적인 감각"을 학습했다는 뜻이다.

## 해석 및 한계

- 파인튜닝 전 마진이 0.03~0.06로 매우 작았다는 것 자체가, 원본 모델이 "대충
  비슷한 주제"만 구분하고 "이 프로젝트의 진짜 정답이 뭔지"는 거의 못 가려냈다는
  뜻이다 (이전에 `eval/RESULTS.md`에서 본 "당뇨병 무슨 약 먹어?"의 치료(0.363) vs
  합병증(0.385) 리랭커 점수 차이가 근소했던 것과 같은 현상).
- 학습 데이터가 25건뿐이라 표본이 매우 작다. test 8개 중 7개를 맞춘 건 고무적이지만,
  통계적으로 확정적인 결론을 내리기엔 부족한 규모 — 더 많은 (질문, 정답청크) 쌍을
  자동 생성(예: LLM으로 청크마다 예상 질문 만들기)해서 재검증하면 신뢰도가 올라간다.
- 이 실험은 `finetune/train.json`의 anchor-positive-negative 쌍 자체에 대한
  판별력만 측정했고, 실제 `/chat` 파이프라인(카테고리 필터링 + 리랭킹까지 거친 최종
  결과)에 이 모델을 교체 투입했을 때 `eval/run_eval.py` 기준 정확도가 어떻게
  바뀌는지는 별도로 확인이 필요하다.

## v2: 학습 데이터 편향 발견 및 보완 (증상 기반 데이터 추가)

v1 학습 데이터를 다시 보니 **`eval/ground_truth.py`의 `GROUND_TRUTH`(병명+카테고리
33문항)에서만 triplet을 만들었고, `SYMPTOM_CASES`(허리가 아파요 같은 증상형 질문)는
전혀 안 썼다는 편향이 있었다.** 더 근본적으로는, negative를 항상 "같은 병의 다른
카테고리"로만 뽑아서, 모델이 배운 건 "한 병 안에서 카테고리 구분하기"뿐이었다.
정작 멀티턴 문진 기능이 의존하는 "증상 설명 → 여러 병 중 맞는 병 찾기"(감별진단)는
학습 신호로 한 번도 들어간 적이 없었던 것.

**보완**: `SYMPTOM_CASES`에서 (anchor=증상 설명, positive=해당 병의 청크,
negative=**다른 병**의 청크) 형태로 6개 triplet을 추가로 만들어(`build_symptom_triplets.py`),
기존 33개와 합쳐(`build_training_data_v2.py`) 39개를 train 30 / test 9로 다시 나누고
재학습했다(`ko-sroberta-finetuned-v2`).

**우려 사항**: 파인튜닝은 "관련 있는 것들을 가깝게" 만드는 과정이라, 잘못하면
전체적으로 다 가까워져서 무관한 질문까지 오염(THRESHOLD 안전장치 무력화)시킬
위험이 있다. 그래서 재학습 후 **거절 테스트(무관한 질문 5개)도 다시 검증**했다.

### 결과

| | train (30) | test/전체 (9) | test/카테고리 (7) | test/증상 (2) |
|---|---|---|---|---|
| 원본 | 76.7% | 55.6% | 42.9% | 100%* |
| **v2** | 100% | **77.8%** | **71.4%** | 100%* |

*증상 테스트가 2개뿐이라 원본도 이미 100%였다 — 표본이 너무 작아서 "증상 데이터
추가가 증상 성능 자체를 끌어올렸다"고 단정할 근거는 부족하다 (정직하게 한계로
남겨둔다). 다만 **카테고리 성능(42.9%→71.4%)과 전체 성능(55.6%→77.8%)은 뚜렷하게
개선**됐고, 증상 데이터를 섞은 게 카테고리 성능을 깎아먹지도 않았다.

**거절 안전성 체크** (무관한 질문 5개 vs 무작위 청크 200개 샘플의 최대 유사도):

| | 최대 유사도 |
|---|---|
| 원본 | 0.394 |
| v2 | 0.375 |

THRESHOLD(코사인 거리 0.5, 유사도로는 0.5 미만이 안전권)를 기준으로 **둘 다
안전권을 유지했고, v2가 오히려 살짝 더 낮았다** — 파인튜닝이 무관한 질문까지
관련 있어 보이게 만드는 부작용은 관찰되지 않았다.

### 재현

```bash
python finetune/build_symptom_triplets.py   # symptom_triplets.json (6건)
python finetune/build_training_data_v2.py   # train_v2.json(30) / test_v2.json(9)
python finetune/train_embedder.py --v2      # ko-sroberta-finetuned-v2/
python finetune/compare_embeddings_v2.py    # 타입별 정확도 + 거절 안전성
```

## 에이전틱 패턴 실험: "LLM이 판단하면 더 나은가?"

RAG 파이프라인의 라우팅(병명/카테고리 판단)을 규칙 기반(문자열 매칭) 대신 **LLM이
tool calling으로 직접 판단**하게 하면 어떨지 실험했다. `llama_cpp`의
`chatml-function-calling` 포맷으로 `search_by_disease_category`,
`search_by_symptom` 두 tool을 정의하고, 15~16문항(병명 언급형 + 증상형)에 대해
규칙 기반과 나란히 비교했다 (두 번 반복 실험, 서로 다른 문항 구성).

### 결과 (두 실험 모두 동일한 패턴)

| | 정확도 | 총 소요시간 |
|---|---|---|
| **규칙 기반** | 12~13 / 15~16 (75~87%) | 3ms ~ 5.6s |
| **에이전틱(tool calling)** | **0 / 15~16 (0%)** | 167s ~ 917s |

tool calling이 뽑아낸 인자 자체가 "총주주", "번번 주로세요", "정확한 병명" 같은
**완전히 망가진 텍스트**였다 (실제 병명이나 증상 요약이 아님).

### 원인 진단: "tool calling이 안 된다"가 아니라 "필드 2개를 한 번에 못 채운다"

처음엔 "이 모델+포맷 조합이 근본적으로 tool calling을 못한다"고 결론 내렸는데,
더 파고드니 틀린 결론이었다. 필드 개수를 바꿔가며 원인을 분리했다:

| 구성 | 결과 |
|---|---|
| 필드 1개짜리 tool 1개 (병명만 추출) | "간흡충증이 뭐야?" → `{"disease_name": "간흡충증"}` **정확** |
| 필드 2개짜리 tool 1개 (병명+카테고리) | "고혈압 원인이 뭐야?" → `{"disease": "원인", "category": "증상"}` — **카테고리에 들어가야 할 값("원인")이 병명 필드에 들어감.** 다른 문항에서는 tool 설명 문구("정확한 병명")를 그대로 베껴오기도 함 |
| **필드 1개짜리 tool 2개를 순차 호출** (병명 추출 → 카테고리 추출, 별도 호출) | 병명 3/3 정확, 카테고리 2/3 정확 — **크게 회복** |

즉 이 8B Q4 모델은 **"질문 하나에서 값 하나만 뽑아내는" 구조화 출력은 잘 하지만,
"질문 하나에서 값 여러 개를 동시에 뽑아 각 필드에 정확히 배치하는" 건 못한다.**
값이 서로 뒤섞이거나, 심지어 자기가 방금 읽은 tool 스키마의 설명 문구를 사용자
질문 내용인 것처럼 착각해서 베껴오기도 한다. 이건 8B Q4 양자화 모델과
`chatml-function-calling`(범용 래퍼, Llama-3.1 네이티브 tool 포맷과 다름)의
조합에서 다중 슬롯 상태 추적 능력이 떨어지기 때문으로 보인다.

**그래도 결론은 바뀌지 않는다**: 순차 호출로 정확도는 회복되지만, 그러려면 원래
1번의 LLM 호출로 되던 걸 2번(병명용, 카테고리용) 호출해야 해서 지연시간이
그만큼 늘어난다. 규칙 기반은 문자열 매칭 한 번(밀리초)으로 끝나는 일을, 에이전틱은
그걸 정확하게 하려면 오히려 더 여러 번의 LLM 호출이 필요하다 — 정확도를 확보하는
비용이 "속도"라는 형태로 그대로 드러난 셈이다.

### 소규모 진단 결과

| | 정확도 | 소요시간 |
|---|---|---|
| **규칙 기반** | 12~13 / 15~16 (75~87%) | 3ms ~ 5.6s |
| **에이전틱 - 필드 2개 한 번에** | 0 / 15~16 (0%) | 167s ~ 917s |
| **에이전틱 - 필드 1개씩 순차 호출 (진단용 3문항)** | 병명 3/3, 카테고리 2/3 | 필드당 1회 호출씩, 총 2배 |

### 전체 16문항 재검증: "고쳤더니 정말 나아졌나?"

진단에서 찾은 방법(1단계 "병명형/증상형" 분류 → 2단계 필드 1개씩 순차 추출)을
`agentic_experiment_v2.py`로 구현해서 16문항 전체에 다시 적용했다. tool은 매
호출마다 항상 1개만, 필드도 항상 1개만 주도록 설계했다.

| | 정확도 | 소요시간 |
|---|---|---|
| 규칙 기반 | 12~13/16 (75~87%) | 3ms~5.6s |
| 에이전틱 v1 (필드 2개 동시) | 0/16 (0%) | 167~917s |
| **에이전틱 v2 (분류 + 순차 단일필드)** | **7/16 (43.8%)** | 474.9s (문항당 평균 약 30s) |

0%에서 43.8%로 크게 회복됐지만, 규칙 기반에는 여전히 못 미친다. 타입별로 쪼개보면
원인이 명확하다:

- **증상형 문항(8개): 5/8 (62.5%)** — 규칙 기반과 비슷한 수준까지 따라옴. 순차
  단일 필드 방식이 "증상 설명을 정리해서 검색용 문구 만들기"에는 꽤 잘 통했다.
- **병명형 문항(8개): 2/8 (25%)** — 여전히 나쁘다. **원인은 필드 추출이 아니라
  그 앞의 "1단계 분류" 자체였다.** "고혈압 원인이 뭐야?"처럼 병명이 명백한 질문
  4개 중 4개를 "증상형"으로 잘못 분류했고, 그중 하나("고혈압 원인이 뭐야?")는
  아예 tool을 호출하지 않고 고혈압 원인에 대한 장문의 에세이를 답변란에 그대로
  써버렸다 (95.8초 소요 — 이 실험에서 가장 느린 호출).

**정정된 결론**: "필드 1개는 잘하고 필드 2개는 못한다"는 진단은 맞았지만 그게
유일한 원인은 아니었다. 이 모델은 **"텍스트를 있는 그대로 뽑아내기"(추출)는 잘하는
반면, "이게 A인지 B인지 고르기"(분류)는 필드가 1개뿐이어도 불안정**했다. 그 결과
병명형처럼 사전 분류가 필요한 경로는 여전히 규칙 기반에 크게 못 미치고, 증상형처럼
"있는 그대로 정리해서 넘기기"만 하면 되는 경로는 꽤 쓸만한 수준까지 올라온다.

즉 이 모델·포맷 조합에서 에이전틱 tool calling은 **"텍스트 추출" 용도로는 실전에
가까운 수준이지만, "여러 선택지 중 하나를 고르는 판단" 용도로는 아직 신뢰하기
어렵다** — 정확도·속도 둘 다 규칙 기반을 못 이기므로 도입하지 않는 게 맞는
결정이며, 이번에도 "측정 없이 버렸다"가 아니라 "고쳐보고, 어디까지 회복되고
어디서 여전히 막히는지 확인한 뒤" 내린 결정이다.

### 재현

```bash
python finetune/agentic_experiment.py       # v1: 필드 2개 동시 (0%)
python finetune/diagnose_tool_calling.py    # 원인 진단 (필드 1개 / 2개 / 순차호출 비교)
python finetune/agentic_experiment_v2.py    # v2: 분류 + 순차 단일필드, 16문항 전체 (43.8%)
```
