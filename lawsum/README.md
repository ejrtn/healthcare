# 판례 요약 AI — 전체 프로세스

비정형 텍스트(판결문 전문)를 읽어서 요약하고, 결과를 검증 가능한 형태로
정리하는 포트폴리오 프로젝트. `llm/`(KDCA 건강정보 RAG 챗봇)과 같은 주제
("비정형 데이터를 구조화된 결과물로 바꾼다")를 법률 도메인으로 적용했다.

이 문서는 "어떻게, 왜 이렇게 처리하게 됐는지" 전체 과정을 설명한다. 1차
버전을 만들어 사람이 직접 평가한 뒤("과정은 괜찮은데 완성도가 떨어진다",
베이스라인 없음·데모 없음·핵심 버그 미해결이 지적됨) 그 피드백을 반영해
처음부터 다시 만든 2차 버전이 지금 이 코드다.

## 전체 파이프라인

```
1. fetch_cases.py   국가법령정보 API에서 판례 수집 (10개 법 분야 키워드)
2. baseline.py       LLM 없이 Lead-3(첫 몇 문장) 추출 — 비교 기준선
3. summarize.py       로컬 Llama-3.1-8B로 "사실관계→쟁점→결론" 3단계 요약
4. evaluate.py        AI 요약 vs 베이스라인 vs 공식 판결요지, 임베딩 유사도 비교
5. app.py            FastAPI 데모 — 판례일련번호 입력하면 즉시 요약 체험
```

각 단계 산출물은 `data/` 아래 쌓인다: `cases.json` → `baseline.json` +
`summarized.json` → `evaluated.json`.

## 1단계: 왜 이 데이터인가, 왜 "판례"인가

국가법령정보 OpenAPI(판례)를 고른 이유는 두 가지다.

1. **완전히 공개된 데이터**: 법적 제약이나 IRB 승인 없이 API 신청만으로
   바로 쓸 수 있다(AI Hub 의료 데이터의 접근 제약과 대비된다).
2. **검증 가능한 정답이 같이 온다**: 판례 본문(`판례내용`)뿐 아니라 법제처가
   직접 작성한 공식 요약(`판결요지`, `판시사항`)이 같은 API 응답 안에
   들어있다. 그래서 "AI 요약이 실제로 괜찮은가"를 수치로 비교할 수 있다.

### 수집 설계: 왜 10개 키워드로 나눴고, 왜 "판결"만 쓰는가

한 키워드로만 검색하면 결과가 한쪽으로 쏠리므로, 서로 다른 법 분야에서
10개 키워드(해고, 임대차, 개인정보, 상속, 이혼, 사기, 교통사고, 명예훼손,
저작권, 계약해제)를 뽑아 분야당 10건씩 가져왔다(`fetch_cases.py`).

1차 버전을 만들 때 실측으로 확인한 문제 두 가지를 이번엔 수집 단계에서
미리 걸러낸다:

- **데이터출처명이 "대법원"이 아닌 것**(국세법령정보시스템, 조세심판원 등)은
  `target=prec`로 상세조회 자체가 안 된다(빈 응답) — 검색 결과에서
  "대법원" 출처만 추린다.
- **판결유형이 "판결"이 아니라 "결정"인 것**(특별항고 각하 같은 절차적
  결정문)은 본안 판단이 아니라서 법제처가 공식 요약(판결요지)을 따로 안
  쓴다. 이런 사건이 섞이면 "비교할 정답 자체가 없는" 상태로 평가에
  들어가서 점수가 왜곡된다 — 1차 버전에서 최하위 2건이 이 문제였다.
  이번엔 `판결유형=="판결"`만 통과시키고, 그래도 혹시 모를 빈 판결요지는
  상세조회 직후 다시 한 번 걸러낸다.

그 결과 분야당 10건을 목표로 했지만, 실제로 "대법원+판결+판결요지 있음"을
전부 만족하는 건 분야마다 5~10건 정도로 줄었다(상속 7건, 계약해제 5건,
나머지는 대부분 10건) — 총 62건.

## 2단계: 베이스라인 — "이게 좋은 숫자인지" 판단할 기준

1차 버전의 가장 큰 결함은 "AI 요약과 공식 요약의 유사도 0.477"이라는
숫자만 있고, 이게 좋은지 나쁜지 비교할 기준이 없었다는 점이다.

`baseline.py`는 LLM을 전혀 쓰지 않고 판결문 맨 앞 세 문장을 그대로 잘라
"요약"이라고 내놓는다(Lead-3, 요약 연구에서 흔히 쓰는 최소 기준선). 판결문
서두는 보통 당사자 정보라서, 이 베이스라인은 의도적으로 "성의 없이 자르면
이 정도"를 보여준다.

추가로 `evaluate.py`에서는 법제처가 쓴 **판시사항**(짧은 공식 headnote)과
**판결요지**(긴 공식 요약)를 서로 비교하는 값도 같이 낸다 — 둘 다 같은
기관이 쓴 공식 문서이니, 이 점수는 사실상 "같은 사건을 다른 사람이 요약해도
이 정도 차이는 난다"는 상한 참고치 역할을 한다.

## 3단계: 요약 — 목표를 바꾸고 9차까지 반복한 기록

`llm/` 프로젝트의 로컬 Llama-3.1-8B(gguf, 4.9GB)를 그대로 재사용한다.
비용 없이 로컬에서 돌리는 원칙(이 세션에서 계속 유지해 온 방향)이고,
모델 파일도 복사하지 않고 `../llm/models/`를 경로로만 참조한다.

### 1~4차: "일반인용 쉬운 요약"으로 시작했다가 한계에 부딪힘

1. "3~5문장으로 요약하라"만 지시 → **판결 주문 한 줄만 떼어내거나, 서두
   당사자 정보를 그대로 베끼는 실패.**
2. "사실관계 → 쟁점/판단근거 → 결론" 3단계 구조를 명시 → **품질 개선**,
   다만 "사실관계"에 법조문 설명이 섞여 들어가는 경우가 남음.
3. "사실관계는 '가./나./다.' 패턴에 있다"고 구조를 짚어줌 → **추가
   개선**(날짜·금액까지 구체적으로 뽑음). 부작용으로 분량이 길어져
   `max_tokens`(600) 한도에 걸려 쟁점·결론이 잘리는 문제 발생.
4. 분량 상한을 명시하고 `max_tokens`를 올림 → **모델이 그 상한을
   일관되게 못 지켰다.** 프롬프트만 더 다듬는 건 수확 체감이 뚜렷했다.

### 목표를 바꿨다: "일반인용 요약"에서 "판결요지 재현"으로

여기서 중요한 방향 전환이 있었다. 원래 목표("판결문을 일반인이 읽기
쉽게 요약")로는 평가할 정답(ground truth)이 없다 — 변호사가 자료를
모아 정리해주는 걸 만들고 싶었지만, 그 품질을 수치로 잴 기준이 없었다.
반면 API가 주는 `판결요지`는 명확한 정답이다. 그래서 **목표를 "원본
판결문만 보고 공식 판결요지를 얼마나 가깝게 재현하는가"로 좁혔다** —
냉정하게는 "일반인용 쉬운 요약기"가 아니라 "판결요지 생성기"가 됐지만,
변호사가 지금 수작업으로 하는 일(판결문을 읽고 요지를 뽑는 일)을
줄여준다는 점에서 그 자체로 실질적 가치가 있고, 무엇보다 **정량 평가가
가능해졌다.**

### 5~9차: 판결요지 스타일로 전환, 그리고 "생성"에서 "추출"로

5. "판결요지 스타일로 직접 작성하라"고 지시 → 유사도 **0.794**(618229
   기준, 4차 0.665). 그런데 조문 일치가 4개 중 1개뿐이었고, 결정적으로
   AI가 **파기된 원심 판단**과 **대법원의 최종 결론**을 혼동해 사실상
   반대 방향의 내용을 써놓은 게 드러났다 — 유사도도 LLM 판정(4점)도 이
   오류를 못 잡아냈다.
6. 62건 전체로 판결요지·판례내용을 실제 텍스트 매칭(`difflib`)했다.
   판결요지의 **평균 85.5%(중앙값 93.7%)가 판례내용에서 그대로 가져온
   텍스트**였고, 그중 79%가 사실관계 서술 **이전**의 법리 설명 구간에서
   나왔다. "다시 써라(생성)"가 아니라 **"그 구간을 찾아 그대로 가져와라
   (추출)"**로 목표를 바꿨다.
7. "그 구간을 찾아서 끝까지 가져오라"고 LLM에게 지시 → 유사도
   **0.936**까지 올랐지만, 조문 일치는 2/4에 그쳤다 — 법리 설명이
   여러 문단에 걸쳐 있는 경우 **모델이 여전히 일찍 멈췄다**(분량 상한
   때와 같은 종류의 한계).
8. "절대 일찍 멈추지 말라"고 더 강하게 지시 → 오히려 더 짧아졌다.
   **"어디서 끝낼지"를 프롬프트로 지시하는 접근 자체가 한계에 도달했다고
   판단**했다.
9. **경계 탐지를 LLM에서 코드로 옮겼다.** `extract_span.py`가 "이유"
   시작부터 사실관계 서술 시작 직전까지를 정규식으로 결정적으로 잘라내고,
   LLM(`CLEANUP_PROMPT`)은 그 안에서 참조판례 괄호·소제목 번호·사실관계
   적용 문장만 제거하는 훨씬 좁은 "다듬기" 작업만 하도록 역할을 나눴다.
   이 구분(참조판례 괄호, 가/나/1/2 소제목, 사실관계 적용 문장이
   제거 대상이라는 것) 자체도 62건 블록 사이 틈을 전수 조사해서 찾아낸
   것이다. 618229에서 유사도 **0.998**까지 나왔다.

### 경계 탐지 버그 3개 — 사람이 직접 읽다가 찾아낸 것들

9차를 62건 전체로 돌린 뒤 결과를 사람이 직접 읽어보다가(`/review`
페이지), 사기 사건 하나(617171)에서 AI 출력에 "1. 사안의 개요", "가.
공소사실의 요지" 같은 소제목과 사실관계 서술이 그대로 남아있는 걸
발견했다. 원인을 추적해 `extract_span.py`의 경계 탐지 정규식이 세 가지
변형 표현을 못 잡고 있었다는 걸 찾아 고쳤다:

- "기록에 **따르면**"만 찾고 있었는데 "기록에 **의하면**"을 쓰는 사건이
  62건 중 19건(31%)이었다.
- "의하면" 뒤에 쉼표(,)가 오는 경우("...기록에 의하면**,** 다음과
  같은...")를 정규식이 허용하지 않고 있었다.
- 형사사건의 40%(25/62건)는 법리보다 **먼저** "1. 사안의 개요"(공소사실
  요지)가 나오는데, 이 섹션을 건너뛰는 로직이 아예 없었다.

세 가지를 고치자 코드 추출 단계만으로도(LLM 호출 전) 판결요지와의
평균 매칭률이 62건 기준 **82.7%**까지 올라갔고, 이게 최종 결과(아래)에
그대로 반영됐다. "지표가 좋아 보여도 직접 몇 건을 읽어보지 않으면
이런 버그는 안 보인다"는 걸 실측으로 재확인한 과정이었다.

## 4단계: 평가 — 세 가지를 나란히

`evaluate.py`는 같은 임베딩 모델(`jhgan/ko-sroberta-multitask`, `llm/`에서
이미 쓰는 것 재사용)로 세 가지 유사도를 계산한다:

- AI 요약 vs 공식 판결요지 (핵심 지표)
- Lead-3 베이스라인 vs 공식 판결요지 (바닥 기준)
- 공식 판시사항 vs 공식 판결요지 (상한 참고치)

AI 요약 점수 하나만 보는 게 아니라 이 세 숫자를 나란히 놓고, "LLM이 Lead-3
베이스라인보다 얼마나 나은지"를 직접 뺄셈으로 보여준다.

## 5단계: 데모(`app.py`)

1차 버전은 스크립트와 JSON 파일만 있고 클릭해볼 수 있는 게 없었다 — 가장
크게 지적된 부분이다. `app.py`는 FastAPI로 두 화면을 제공한다.

- `/` — 판례일련번호를 입력하면 즉시 API에서 본문을 받아 로컬 Llama로
  요약하고, 원본 전문 → 유사도 → 공식 판결요지/AI 요약을 좌우로 나란히
  보여준다. 전부 잘리지 않고 전체 텍스트가 나온다.
- `/review` — 이미 계산해둔 62건 평가 결과 중, 10개 법 분야마다 유사도가
  가장 낮았던 사건 1건씩을 아코디언(접힌 목록)으로 모아서 보여준다.
  LLM을 다시 부르지 않고 `data/evaluated.json`을 그대로 렌더링해서
  즉시 뜬다 — 사람이 직접 저품질 사례를 훑어보기 위한 화면이고, 실제로
  이 화면에서 읽다가 경계 탐지 버그 3개를 찾아냈다.

`uvicorn app:app --reload --port 8003`으로 실행.

## 4차~6차: 코드로 경계를 자르던 방식을 버리고, LLM이 의미로 찾게 하다

3차(위 결과, 0.714)까지는 `extract_span.py`가 정규식으로 "법리 설명
구간이 어디서 시작해 어디서 끝나는지"를 코드로 결정적으로 자르고, LLM은
그 안에서 소제목·참조판례만 제거하는 좁은 역할만 했다. 문제는
`extract_span.py`가 "사안의 개요", "원심의 판단" 같은 변형 표현을 하나씩
실측으로 찾아 계속 메꿔야 했고, 그래도 619451·241863 같은 사건은 여러
차례 수정이 필요했다는 것 — 판결문의 구조가 사건마다 미묘하게 달라서
코드로 모든 경우를 다 잡기 어려웠다.

**4차**: 경계를 코드로 안 자르고, "법리는 이런 형태다"라고 긍정적으로만
정의한 뒤 LLM이 판례내용 전문에서 직접 찾게 했다. 처음엔 "법리와
사실관계를 구분하는 신호 5가지"(등장인물 유무, 날짜 유무 등) 같은
제외/구분 규칙도 같이 줬는데, 그러면 한 사건은 고쳐지고 다른 사건이
깨지는 패턴이 반복됐다(618229/619451/241863 기준 0.998/0.946/0.336).
제외 규칙을 전부 빼고 "법리는 이런 것이다"만 긍정적으로 정의하자 세
사건 다 가장 좋았다(0.998/0.991/0.996) — 8B 모델에게는 "이건 빼라"
나열보다 "이게 맞는 것이다" 하나만 정의하는 쪽이 훨씬 안정적이었다.
이 프롬프트로 62건 전체를 돌리니 평균 0.791까지 올랐지만, 618177·240823
두 건이 완전히 빈 요약(0자)을 냈다.

원인을 두 사건의 **공식 판결요지를 직접 읽어서** 확인했다("법리만 보면
안 되는데"라는 지적이 출발점이었다) — 판결요지는 보통 "[1] 추상적
법리"뿐 아니라 "[2] 그 법리를 이 사건에 적용해 결론을 낸 설명"(甲,
피고인처럼 당사자를 가리키는 말 포함)까지 둘 다 포함하는데, 4차
프롬프트는 "당사자 이름을 쓰지 않는다"를 법리의 특징으로 못박아 [2]를
배제하도록 유도하고 있었다. 이 두 사건은 [1]이 짧고 [2]가 본문의
대부분이라, LLM이 찾을 게 없다고 보고 제목 한 줄만 뱉은 것이었다.

**5차**: 그래서 정의 자체를 "법리"에서 "법리 + 그 적용(당사자 지칭
허용)"으로 넓혀 프롬프트를 통째로 교체했다. 실패했던 7건 기준으로는
전부 개선됐지만, 62건 전체로 돌려보니 평균이 오히려 **0.791 → 0.713**로
떨어졌다. 사건별로 대조해보니 614379(0.964→0.159), 624225(0.953→0.201),
607789(0.978→0.416) 등 원래 "순수 법리형" 판결요지였던 15건이 크게
나빠져 있었다 — 그 사건들의 공식 판결요지에는 적용부가 없는데, "항상
적용부까지 포함하라"는 넓어진 정의가 불필요한 내용을 끌어들인 것.
"법리만"과 "법리+적용" 둘 다 62건 중 일부에만 맞는 정의였다 — 판결요지
스타일이 사건마다 다르다는 뜻이다.

**6차(최종)**: 둘 중 하나로 통일하는 대신, 4차 프롬프트(법리만, 평균
0.791)를 기본으로 쓰고, 그 결과가 거의 비었을 때만(20자 미만 — LLM이
법리 단독 구간을 못 찾았다는 신호) 5차 프롬프트(법리+적용)로 한 번 더
시도하는 2단계 구조로 바꿨다. "이런 내용은 빼라"는 사건 내용 기반
제외 규칙이 아니라 "1차 결과가 비정상일 때만 더 넓은 정의를 쓴다"는
실행 조건이라, 4차/5차 전환 때 반복됐던 "제외 규칙 늘릴수록 다른 사건이
깨지는" 패턴이 재발하지 않았다 — 나머지 60건은 그대로 4차 결과를 쓰고,
실패했던 두 건만 구제된다.

## 모델 비교: 한국어 특화 모델로 바꾸면? (Kaggle GPU) — `kaggle_summarize.py`

판결문은 한국어이고 "원문을 그대로 옮기는" 작업이라, 한국어에 특화된 모델이 더 나은지 확인했다. 프롬프트(12차:
법리만 → 거의 비면 법리+적용)와 후처리는 그대로 두고 **모델만** 바꿨다. 로컬 기록(CPU, Llama 4bit GGUF)과 실행
환경이 달라지므로 Llama도 같은 환경(Kaggle T4×2, vLLM, FP16, temperature 0.2)에서 다시 돌려 세 모델을 같은
조건으로 비교했다.

- **A.X가 크게 앞섰다**: 같은 사건끼리 비교하면 Llama보다 0.02 넘게 좋은 사건 26건, 나쁜 사건 5건.

- **점수가 오른 이유는 "일찍 멈추지 않는 것"**: 이 프로젝트 내내 문제였던 "법리 구간을 끝까지 안 가져오고 일찍
  멈춤"(4·7·8차)이 Llama에서는 여전했다 — 62건 중 33건이 공식 판결요지 길이의 절반도 안 됐다. A.X는 9건뿐이고

## 알려진 한계 (정직하게 기록)

- **느리다**: CPU로 돌리는 8B 모델이라 판례 1건 요약에 수 분씩 걸린다.
  62건 전체 처리에 매번 몇 시간이 걸렸고, GPU 없는 환경의 현실적
  한계라 해결하지 않고 그대로 남겨둔다.
- **LLM에게 "하지 마라"를 맡기면 자주 실패한다**: 분량 상한(4차 프롬프트),
  구간을 끝까지 가져오기(7~8차), 다듬기 단계의 소제목·참조판례
  제거(9차), 법리/사실관계 구분 신호 5가지(10차) — 전부 "이건 하지
  마라/빼라"를 LLM에게 지시로 시킨 부분에서 반복적으로 실패했다. 반대로
  "코드로 경계를 자르거나"(3차) "이게 맞는 것이다만 긍정적으로
  정의하거나"(4차) 할 때는 안정적이었다 — 이 프로젝트에서 가장 많이
  재확인된 패턴이다. 다만 4차→5차에서 드러났듯, 긍정적 정의라도 "모든
  사건에 하나의 정의를 통일 적용"하면 사건마다 다른 판결요지 스타일
  때문에 똑같이 깨질 수 있다. 최종적으로 안정적이었던 조합은 "기본
  정의 하나를 쓰고, 결과가 명백히 비정상일 때만 조건부로 다른 정의를
  보조로 쓰는" 구조(6차)였다 — 이건 "내용을 보고 제외"가 아니라
  "결과물의 길이로 실패를 감지해서 대응"이라는 점에서 반복 실패했던
  제외 규칙들과는 성격이 다르다.
- **경계 탐지가 100%는 아니다**: 3차(코드 기반)든 6차(LLM 의미판단
  기반)든 62건 중 일부(국제사법이 얽힌 복잡한 사건, 법리와 적용이
  유독 강하게 섞인 사건 등)는 구조가 달라 여전히 깨끗하게 안 잘린다.
  `/review`에서 직접 확인 가능.
- **LLM 샘플링 자체의 변동**: temperature=0.2로도 완전히 결정적이지는
  않다. 6차에서 609501·241881(이혼) 두 건이 별다른 코드 변경 없이도
  3차 대비 5~10%p 떨어졌는데, fallback이 작동한 사건이 아니라는 점에서
  순수한 run-to-run 변동으로 보인다 — 법률 도메인처럼 "원문과 똑같이"가
  목표인 작업에서는 이런 비결정성 자체가 한계로 남는다.
- **"이미 정답이 있는 사건을 재현하는" 데모라는 개념적 한계**: 이 프로젝트가
  쓰는 판례는 전부 법제처 공식 요약이 이미 존재하는 것들이다. 실제 제품
  가치는 공식 요약이 없는 하급심 판결 등에 있는데, 이번 데모는 그 상황을
  보여주지 못한다 — 평가를 위해 정답이 필요했던 것과, 실제 쓰임새가
  정답이 없는 곳이라는 점 사이의 간극을 정직하게 남겨둔다.
