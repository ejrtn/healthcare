# Clinical Note LLM — 진료 대화 → 구조화된 진료기록

> 진행 중 (2026-10-27 시작, 목표 완료 2026-11-10)

의사-환자 진료 대화 전체(평균 약 1,200단어)를 읽고 SOAP 형식의 진료기록을
JSON으로 생성하는 소형 LLM을 직접 학습(SFT)하고, vLLM으로 서빙 최적화까지
측정하는 프로젝트.

## 데이터

| 데이터셋 | 용도 | 규모 | 라이선스 |
|---|---|---|---|
| [ACI-BENCH](https://github.com/wyim/aci-bench) | 학습 + **최종 평가** (진료 1회 전체 대화 → 전체 기록) | train 67 / valid 20 / test 120 | CC BY 4.0 |
| [MTS-Dialog](https://github.com/abachaa/MTS-Dialog) | 학습 보조 (짧은 대화 → 기록 섹션 하나) | train 1,201 / valid 100 / test 400 | CC BY 4.0 |

`bash scripts/download_data.sh`로 받는다 (커밋 고정).

데이터 분석 메모:
- ACI-BENCH 대화 길이: 중앙값 약 1,240단어, 최대 3,050단어 / 진료기록 중앙값 약 400단어
- ACI-BENCH 기록의 섹션 제목이 사건마다 다르다 (CHIEF COMPLAINT, HPI, ROS,
  PHYSICAL EXAM, RESULTS, ASSESSMENT AND PLAN 등) → SOAP 3개 필드로 정규화 필요
- ACI-BENCH에는 같은 대화의 **ASR 원본 / ASR 교정 / 사람 전사** 버전이 있다
  → 음성인식 오류에 대한 강건성 측정 가능
- ACI-BENCH 저장소에 공식 평가 코드(ROUGE, BERTScore, UMLS 기반 MEDCON)와
  논문 기존 모델(BART, LED 등) 예측 결과가 있다 → 같은 기준으로 비교

## SFT 데이터

- train 79건 = ACI train 67 + 같은 진료의 ASR 원본 전사본 12건(`train_virtscribe_asr`, 음성인식 잡음 증강)
- `train_aci_asrcorr` 35건은 challenge train과 대화가 사실상 같아(29건 완전 동일) 제외. 평가 분할과 겹치는 기록 0건
- valid 20건 (ACI valid)
- 토큰 길이(Qwen2.5 토크나이저): 전체 중앙값 2,520 / 최대 4,681, 정답 JSON 중앙값 671
  → `max_length=4800`으로 잘리는 예시 없음

## 평가

- 출력 JSON 스키마 = ACI-BENCH 공식 평가가 나누는 4구역
  (`subjective`, `objective_exam`, `objective_results`, `assessment_and_plan`).
  구역 분리는 공식 코드의 SectionTagger를 그대로 옮겨 쓴다 (`src/sectiontagger.py`).
  정답 기록을 4구역으로 나눴다가 다시 합쳐도 67/67건 동일, 원문 보존율 99.8%.
- 채점기(`src/evaluate.py`): 전체 기록 + 구역별 ROUGE. 공식 결과 파일과 비교하면
  ROUGE-1이 0.2점 정도 어긋난다(BioBART test2: 39.00 vs 공식 39.20). 그래서 논문 표를
  인용하지 않고, 저장소에 있는 기존 모델 예측을 **같은 채점기로 재채점**해 비교한다.

- **형식 실패**: 자유 텍스트 3B는 프롬프트로 지정한 제목 대신 `**ASSESSMENT AND PLAN:**`처럼 마크다운으로

  넘길 출력이라면 형식 보장이 필요하다는 근거.
- **JSON 강제도 100%가 아니다**: 깨진 출력은 전부 같은 구절 반복(`no leg pain, no leg swelling, ...`)으로
  max_tokens(2048)에 걸린 경우다. 문법 강제는 생성이 끝나야 닫는 괄호를 쓸 수 있다.
- **채점 함정**: JSON 값 안에 섹션 제목을 빼먹는 경우가 많아(3B 112건 중 75건 구역 어긋남), 합친 텍스트를
  다시 나누면 내용과 무관하게 점수가 깎였다. JSON 예측은 모델이 키로 나눈 구역을 그대로 채점하도록 수정.
- 7B는 사실을 옮기는 O-exam·O-results에서 GPT-4보다 높지만, 3B·7B 모두 **S·A&P가 GPT-4보다 낮다** → SFT 목표.
- 전체 ROUGE-1은 모든 시스템이 45~51로 붙어 있어 변별력이 낮다. 구역별 점수를 주 지표로 본다.

`results/baseline_*.json`의 점수는 채점기 수정 전 값이다. 최신 점수는 `src/summarize_runs.py`가 예측을
다시 채점해 만든 `results/runs.md`를 기준으로 한다.

#### 오류 분석: 잘림 = 같은 줄 반복 루프

잘린 34건은 모두 한 줄을 끝없이 반복하다 max_tokens(2048)에 걸린 경우다
(예: `• Endocrine: Denies weight changes.`가 수십 번). 출처별로 나누면 원인이 보인다.

| 출처 (진료 방식) | 학습 건수 | 학습 기록 중 ROS 목록 비율 | 테스트 잘림 비율 |
|---|---|---|---|
| aci (자연스러운 대화를 옆에서 녹음) | 35 | 94% | 17/66 (26%) |
| virtassist (의사가 음성비서에 지시) | 20 | 75% | 5/30 (17%) |
| virtscribe (의사가 기록 담당에게 받아쓰기 지시) | 12 | 17% | **12/24 (50%)** |

- 학습 기록 67건 중 50건이 ROS(계통별 문진) 목록을 갖는다. 모델이 이 다수 스타일을 학습해,
  ROS가 없는 짧은 기록(virtscribe에 많고, virtassist에도 있다. 예: test1 D2N092 — virtassist, 정답 152단어,
  ROS 없음)에도 ROS 목록을
  쓰기 시작한다. 대화에 근거가 없으니 일반적인 음성 소견을 지어내다 반복에 빠진다 → **환각과 루프가 같은 뿌리**.
- 대응 1 (디코딩): 반복 벌점을 **검증셋에서만** 골라 테스트에 한 번 적용 → 아래 결과.
- 대응 2 (학습, 여유 시): 소수 스타일 비중 조정, 또는 대화에 근거 없는 문장을 벌주는 DPO.

### 반복 억제 탐색 (검증 20건, SFT 3B) — `kaggle/04_decode_sweep.py`

| repetition_penalty | frequency_penalty | 구역 평균 R1 | 전체 R1 | JSON 유효 | 잘림 |
|---|---|---|---|---|---|
| 1.0 | 0.0 | 40.4 | 45.7 | 75% | 5 |
| 1.0 | 0.1 | 49.8 | 56.0 | 100% | 0 |
| 1.0 | 0.2 | 50.1 | 54.3 | 100% | 0 |
| **1.0** | **0.4** | **50.5** | 57.1 | 100% | 0 |
| 1.05 | 0.0 | 41.2 | 48.1 | 75% | 5 |

- frequency_penalty는 0.1만으로 루프가 사라지고, 0.1~0.4 사이 차이는 0.7점 이내로 안정적이다.
- repetition_penalty는 입력(대화)에 나온 토큰까지 벌점을 주므로 약하게(1.05) 걸면 루프를 못 끊고,
  세게 걸면 대화의 의학 용어를 옮겨 적지 못하게 된다. 생성한 토큰에만 벌점을 주는 frequency_penalty가 맞다.

### 근거 검사: 점수는 올랐지만 지어낸 내용이 늘었다 — `src/faithfulness.py`

ROUGE는 정답과 단어가 겹치는 정도만 본다. 테스트 10건을 대화 원문과 한 줄씩 대조했더니(점수 크게 오른 3건,
보통 2건, 떨어진 3건, 반복 루프 2건), 학습 후 모델은 정답 문체를 잘 따라 하면서 대화에 없는 내용을 지어냈다.

| 10건 직접 대조 | 학습 전 3B | 학습 후 3B |
|---|---|---|
| 사실과 반대 (예: 실금 1회 → "denies incontinence") | 4곳 | 6곳 |
| 지어냄, 나이·성 제외 (예: 찍지 않은 MRI 9건과 그 결과, "Allergies: Motrin") | 1곳 | 12곳 |
| 대화에 없는 나이·성을 쓴 기록 | 0건 | 4건 |
| 치료 계획 핵심 항목 누락 (예: 계획 칸이 병력 복사본) | 2건 | 8건 |

기계로 확인하기 쉬운 항목은 120건 전체에서 셌다. 정답 기록도 같은 기준으로 재서 기준선으로 쓴다.

| 120건 자동 검사 | 대화에 없는 나이를 쓴 기록 | 근거 없는 숫자 (나이 제외) | 대화에 없는 검사를 쓴 기록 |
|---|---|---|---|
| 정답 기록 | 40 | 10.8% | 1 |
| 3B 학습 전 | 0 | 9.8% | 1 |
| **3B 학습 후** | **54** | **12.8%** | **3** |
| 7B 학습 전 (참고) | 0 | 7.1% | 0 |
| **3B 2차 학습 (근거 정리 데이터)** | **0** | **12.0%** | **1** |

- **원인 하나는 데이터다.** 정답 기록에는 대화에 없는 나이·성이 있다(40/120건 — 기록 작성자가 진료 정보
  시스템을 보고 채운 것으로 보인다). 모델은 대화만 보므로 이것을 배우면 "지어내는 법"을 배운다. 학습 후 모델은
  정답(33%)보다도 자주(45%) 나이를 지어낸다.
- **대응: 데이터를 고쳐 다시 학습** — `build_sft_data.py --grounded`로 정답에서 대화에 근거 없는 나이·성을 지운
  학습 데이터(99건 중 47건, 97곳 수정)를 만들고, 다른 설정은 그대로 두고 재학습했다.
  **지어낸 나이 54건 → 0건, 대화에 없는 검사 3건 → 1건, ROUGE-1은 55.5 → 55.7로 그대로.**
  점수를 잃지 않고 환각의 한 종류를 없앴다. 근거 없는 숫자(12.8 → 12.0%)는 거의 그대로라 데이터 정리로 고칠
  수 있는 범위가 아니다 → 다음 대상.
- "사실과 반대" 오류는 학습 전 모델에도 있어(의사의 질문 목록을 부정문으로 옮기는 패턴) 데이터 정리만으로는 줄지
  않을 수 있다 → DPO 후보.
- 이후 모든 결과표에 ROUGE와 근거 검사를 나란히 싣는다.

### DPO 1차: 지어낸 숫자는 줄었지만 "사실과 반대"는 그대로 — `kaggle/05~07`, `src/build_dpo_pairs.py`

2차 SFT 모델로 학습 대화 79건마다 후보 8개를 샘플링하고, Qwen2.5-14B(AWQ) 판정 모델이 후보마다 "대화와 반대"·
"대화에 없는 사실"을 근거와 함께 뽑았다. 벌점(판정 + 규칙 검사)이 가장 낮은 후보를 좋은 답, 2점 이상 높은 후보를 나쁜 답으로
짝 110개(검증 22개)를 만들어 DPO(beta 0.1, LoRA r16, 2 epoch, T4×2 29분)로 학습했다. 내용을 빼서 벌점을 피하는 답이 좋은 답이
되지 않도록, 좋은 답은 ROUGE·근거 있는 숫자 수·길이가 나쁜 답보다 크게 낮지 않아야 한다는 조건을 걸었다.

| 테스트 120건 | ROUGE-1 | JSON 유효 / 잘림 | 근거 없는 숫자 (규칙) | 기록에 쓴 숫자 | 대화에 없는 사실 (판정, 기록당) | 대화와 반대 (판정, 기록당) |
|---|---|---|---|---|---|---|
| 3B 학습 전 | 45.8 | 100% / 0 | 9.8% | 438 | 3.22 | 0.82 |
| 1차 SFT | 55.5 | 100% / 0 | 12.8% | 549 | 3.80 | 1.15 |
| 2차 SFT (근거 정리) | **55.7** | 99.2% / 1 | 12.0% | 559 | 4.39 | 1.21 |
| **2차 SFT + DPO** | 55.0 | 95.0% / 6 | **9.0%** | 500 | **3.78** | 1.21 |

- **좋아진 것**: 근거 없는 숫자 비율 12.0 → 9.0%(학습 전 수준), 판정 기준 대화에 없는 사실 4.39 → 3.78건/기록.
- **안 좋아진 것**: "대화와 반대"는 그대로(1.21). ROUGE -0.7, 출력이 잘린 기록 1 → 6건.
- **꼼수 학습이 일부 나타났다**: 기록에 쓴 숫자가 559 → 500개로 줄었고, 그중 근거 있는 숫자도 492 → 455개(-7.5%)로 줄었다.
  짝 조건으로 막으려 했지만 완전히 막지는 못했다. 반대로 기록은 평균 395 → 444단어로 길어졌다. 짝의 좋은 답이 나쁜 답보다
  평균 14% 길어서(404 vs 355단어) "길게 쓰기"까지 배운 것으로 보이고, 잘림 증가와도 맞물린다(DPO의 알려진 길이 편향).
- **학습 신호가 약했다**: 학습 짝 정답률은 100%까지 올랐지만 검증 짝 정답률은 68%, 보상 차이(margin)는 0.08에 그쳤다 →
  짝 110개에 과적합.

**원인: 판정 모델이 부정확했다.** 2차 SFT 결과에서 판정 모델이 "대화와 반대"로 표시한 것 15개를 무작위로 골라 대화 원문과
직접 대조했다.

| 판정 모델의 "대화와 반대" 15개 | 개수 | 예 |
|---|---|---|
| 실제로 대화와 반대 | 8 | 기록 "하루 두 번" ↔ 대화 "하루 한 번으로 줄였다", 기록 "야간 호흡곤란 없음" ↔ 대화 "일주일 전 한 번 있었다" |
| 반대가 아니라 대화에 없는 내용 (종류를 잘못 분류) | 3 | "흉통 없음" ↔ 대화에서 묻지 않음 |
| 문제없음 (판정 오류) | 4 | 기록 "발열 없음" ↔ 대화 "아니요, 못 느꼈어요" |

또 이 문제를 처음 찾게 한 사례(D2N201, 실금 1회 → "denies incontinence")를 놓쳤다. 정밀도 약 50%인 판정으로 짝을 고르니
"좋은 답"에도 반대 오류가 평균 0.95개 남아 있었고(나쁜 답 1.8개), 모델이 무엇을 피해야 하는지 배우기 어려웠다.

→ **다음 단계**: 판정을 "기록 전체에서 문제 찾기"에서 **"부정문 하나하나 확인하기"**로 좁힌다(기록의 "denies X / no X"마다
"대화에서 환자가 X가 있다고 했나?"를 묻는다). 짝은 좋은 답과 나쁜 답의 길이를 비슷하게 맞춰 길이 편향을 없앤다.

### 차트 + 대화: 실제 진료처럼 차트를 함께 준다 — `kaggle/08_extract_chart.py`, `src/build_chart_data.py`

정답 기록의 "대화에 없는" 나이·이름·혈압·지난 검사 수치는 기록 작성자가 차트(EHR)를 보고 쓴 것이다. 의사는 차트를
보면서 대화하므로, 입력도 "차트 + 대화"여야 한다. ACI-BENCH에는 차트가 없어 정답 기록에서 거꾸로 복원했다.

- **복원**: Qwen2.5-14B가 대화·정답 기록을 읽고 진료 전부터 차트에 있었을 정보(이름·나이·성별·활력징후·지난 검사·과거력·
  약·알레르기)를 뽑는다. 대화에 나왔든 안 나왔든 넣는다 — 처음에는 "대화에 없는 것만" 넣었다가, 사례마다 차트 내용이
  들쭉날쭉해져 모델이 차트의 역할을 잘못 배울 수 있어 바꿨다.
- **걸러내기(규칙)**: 정답 기록에 없는 값(추출 모델이 지어냄), 이번 진료의 판단(진단·계획·"의심"·검사 처방 — 답 누설),
  "N/A" 같은 빈칸 말, 값 없는 활력징후 이름. 직접 대조로 테스트 17/120건의 차트에 당일 검사 결과가 들어 있음을 확인
  — 실제 EHR에 있는 정보라 유지했지만 RESULTS 구역 점수는 차트를 준 것만으로 오를 수 있다.
- **같은 근거로 평가**: 근거 검사의 "근거"를 차트 + 대화로 바꾸면 정답 기록의 근거 없는 숫자는 10.8 → 4.5%, 지어낸
  나이는 40 → 0건 — 정답의 "대화 밖 정보"는 대부분 차트로 설명된다.

| 테스트 120건 (근거 = 차트 + 대화) | ROUGE-1 | S | O-exam | O-results ※ | A&P | 근거 없는 숫자 | 지어낸 나이 |
|---|---|---|---|---|---|---|---|
| 정답 기록 | – | – | – | – | – | 4.5% | 0 |
| 3B 학습 전 + 차트 | 47.2 | 38.7 | 50.6 | 39.2 | 34.1 | 4.0% | 0 |
| **3B 차트 SFT** | **56.1** | **52.7** | 47.2 | 65.5 | **42.4** | 6.8% | **16** |
| (참고) 2차 SFT, 대화만 (근거 = 대화) | 55.7 | 50.7 | 45.2 | 54.6 | 42.8 | 12.0% | 0 |

※ 당일 검사 결과가 차트에 있는 17건 때문에 O-results는 대화만 쓴 모델과 직접 비교하지 않는다.

- 차트를 주면 학습 전 모델도 근거 없는 숫자가 정답 수준(4.0%)이다. 학습한 모델은 ROUGE 56.1로 가장 높지만, 근거 없는
  숫자 6.8%로 정답(4.5%)보다 많다.
- **차트에 나이가 없는 29건 중 16건에서 45·50·65세 같은 나이를 지어냈다.** 학습 데이터는 깨끗하다(차트에 나이가 없는
  20건 중 19건은 정답에도 나이가 없다). 하지만 학습 정답 57/79건이 "NN-year-old"로 시작해 "나이를 쓰는 습관"이
  20건의 반례보다 강했다. 나이를 지운 2차 데이터(34/79건만 나이 있음)에서는 0건이었다.
- 원인은 복원 방식에 있다: 실제 EHR에는 나이가 항상 있지만, 정답 기록에 나이가 없으면 복원할 수 없어 차트에서 빠졌다.

#### 차트 2차: 모든 차트에 이름·나이·성별을 채운다 — `src/demographics.py`

실제 EHR처럼 모든 차트에 이름·나이·성별을 넣었다. LLM에게 채우게 하지 않고 **규칙으로만** 채운다. 순서는 정답 기록의
소개 문장("Martha Collins is a 50-year-old female") → 대화 속 소개·인사("hi, martha") → 기록 내용으로 범위를 정한
무작위(학생이면 18~24세)다. 값마다 출처를 남긴다(219건 중 나이 181건은 기록·대화에서 찾고, 38건은 무작위).
219건을 LLM 복원 차트와 모두 대조하며 규칙을 고쳤다. 가족 나이("her 9-year-old brother")나 증상이 시작된 나이
("since age 12")를 환자 나이로 읽는 오류, "75 y.o."·"22-month-old" 같은 표기를 못 읽는 오류 등이다. 고친 뒤 남은
경고는 1건으로, 정답 기록에 "male"이라고 쓰고 she/her를 29번 쓴 오타다(대명사를 따름). 모르는 항목은 줄을 빼지
않고 "not recorded"로 적는다.

| 테스트 120건 (근거 = 차트 + 대화) | ROUGE-1 | S | O-exam | O-results ※ | A&P | 근거 없는 숫자 | 지어낸 나이 |
|---|---|---|---|---|---|---|---|
| 정답 기록 | – | – | – | – | – | 4.5% | 0 |
| 3B 학습 전 + 차트 2차 | 47.3 | 38.3 | 50.4 | 38.0 | 35.1 | 4.2% | 0 |
| 차트 1차 SFT (위) | 56.1 | 52.7 | 47.2 | 65.5 | 42.4 | 6.8% | 16 |
| **차트 2차 SFT** | **56.8** | 52.6 | 49.0 | 67.8 | **43.3** | 9.7% → **5.4%** † | **0** |
| 차트 2차 SFT, 채운 값을 지운 차트 ‡ | 57.0 | 52.8 | 47.3 | 68.5 | 42.9 | 7.0% → 5.4% † | 15 |

† 1건(D2N191)이 같은 구절을 끝없이 되풀이하다 잘렸고(JSON 깨짐), 그 안의 "130" 반복 등 근거 없는 숫자 26개가
전체 비율을 끌어올렸다. 이 1건을 빼면 5.4%로 정답(4.5%)에 가깝다. 차트 1차는 이 사례를 빼도 6.8% 그대로다.
‡ 스트레스 테스트. 규칙으로 채운 값을 지우고 추출 단계 값만 남겨, 차트에 "Age: not recorded"인 29건을 만들었다.

- **나이를 지어내는 문제가 사라졌다 (16 → 0건)**: 차트에 나이가 있으면 모델은 차트의 나이를 그대로 쓴다. ROUGE와 A&P도
  조금 올랐다. 실제 EHR에는 나이가 항상 있으므로 이것이 실제 사용 조건이다.
- **하지만 "not recorded"를 보고 쓰지 않는 법은 배우지 못했다 (15/29건)**: 학습 차트에는 나이가 항상 있어서, 나이 칸이
  "not recorded"인 예를 본 적이 없다. 이 테스트는 학습 분포 밖이다. 이 행동까지 원하면 학습 데이터의 일부(예: 10%)에서
  나이를 일부러 "not recorded"로 바꾸고, 그때 정답에서도 나이를 지운 짝을 넣어야 한다.
- **남은 약점**: 같은 구절을 반복하다 멈추지 않는 출력이 120건 중 1건 있었다. 서빙에서는 max_tokens와 반복 감지로
  잘라내야 한다.

#### 차트 3차: "빈칸 = 없음"을 학습 짝으로 가르친다 — `build_chart_data.blank_age_example`

모르는 항목을 "not recorded" 대신 빈칸("Age:")으로 두고, 지시문에 "빈 차트 칸은 그 정보가 없다는 뜻"을 더했다. 표기만
바꿔서는 배우지 못하므로, 같은 대화로 **나이 칸만 다른 짝**을 만들어 학습에 넣었다. 원래 예는 "Age: 63"에 정답
"a 63-year-old male", 짝은 "Age:"에 정답 "a male"이다. 환자가 대화에서 나이를 말한 사례는 빈칸이어도 나이를 써야 하므로
짝을 만들지 않았다. 학습 79건에 짝 19건을 더해 98건이 됐다.

| 테스트 120건 | ROUGE-1 | S | O-exam | O-results | A&P | 근거 없는 숫자 | 지어낸 나이 |
|---|---|---|---|---|---|---|---|
| 차트 2차 SFT | 56.8 | 52.6 | 49.0 | 67.8 | 43.3 | 9.7% (1건 빼면 5.4%) | 0 |
| **차트 3차 SFT** | **58.0** | 53.1 | 49.3 | 65.2 | **43.8** | **4.2%** | **0** |
| 차트 2차 SFT, 빈칸 차트 ‡ | 57.0 | 52.8 | 47.3 | 68.5 | 42.9 | 7.0% | 15/29 |
| 차트 3차 SFT, 빈칸 차트 ‡ | 57.6 | 52.4 | 48.6 | 65.6 | 43.3 | 5.5% | 11/29 |

‡ 같은 스트레스 테스트. 2차는 "Age: not recorded", 3차는 "Age:"로 적힌 29건이다.

- **실제 사용 조건(채운 차트)은 더 좋아졌다**: ROUGE-1 58.0으로 지금까지 가장 높고, 근거 없는 숫자는 4.2%로 정답 기록
  (4.5%)보다 낮다. 끝없이 반복하는 출력도 이번에는 없었다.
- **빈칸을 보고 나이를 쓰지 않는 행동은 조금만 늘었다 (15 → 11/29건)**: 남은 11건은 모두
  "Jacqueline is a pleasant 45-year-old female" 꼴로, 학습 기록에서 자주 본 문장 틀에 흔한 나이(45·50·65)를 끼워 넣었다.
  원인은 분포 차이로 보인다. 학습 짝은 나이 칸만 비웠지만, 이 테스트 29건은 **모두 이름 칸도 비어 있다**(12건은 성별까지).
  모델은 "이름·나이가 함께 빈 차트"를 학습에서 본 적이 없다. 짝도 19건으로 적다.
- **판단**: 실제 EHR에는 이름·나이·성별이 항상 있으므로 채운 차트 조건을 기준으로 삼고, 차트 3차 모델을 최종 모델로 쓴다.
  빈칸 행동을 더 끌어올리려면 이름까지 비운 짝을 만들어야 하는데, 정답 기록에서 이름을 지우려면 문장을 고쳐 써야 한다
  ("Martha Collins is" → "The patient is"). 그래서 이번 범위에서는 하지 않았다.

## 서빙 벤치마크 (vLLM 0.32, T4, SFT 3B) — `kaggle/03_serving_bench.py`

`vllm serve`로 실제 OpenAI 호환 서버를 띄우고, 비동기 스트리밍 클라이언트로 동시 요청 수를 1→32로 늘리며
측정했다. 입력은 테스트 대화(평균 약 1,700토큰), 출력 최대 1,024토큰, temperature 0, frequency_penalty 0.4.

2차 학습 모델(근거 정리 데이터)로 잰 값이다. 동시 요청 단계마다 아직 보내지 않은 대화를 쓴다(아래 측정 방법 메모).

| 설정 | 가중치 메모리 | KV 캐시 | 동시 1: TPOT | 동시 1: E2E | 동시 32: TPOT | 동시 32: 출력 tok/s | 동시 32: E2E p50 |
|---|---|---|---|---|---|---|---|
| FP16, T4×1 | 5.8 GB | 175k 토큰 | 34 ms | 22.4 s | 143 ms | 195 | 94 s |
| FP16, T4×1, JSON 스키마 강제 | 5.8 GB | 188k | 34 ms | 16.8 s | 149 ms | 180 | 89 s |
| FP16, T4×2 (Tensor Parallel) | 2.9 GB/GPU | 543k | **17 ms** | **11.9 s** | **77 ms** | **357** | **54 s** |
| AWQ 4bit, T4×1 ‡ | **2.0 GB** | 287k | **15 ms** | – | 134 ms | 200 | – |

TPOT = 첫 토큰 이후 토큰 하나당 시간, E2E = 진료기록 한 건 완성까지 걸린 시간.
‡ 우리 SFT 모델이 아니라 같은 구조의 공식 `Qwen2.5-3B-Instruct-AWQ`(학습 전)로 잰 **속도 참고값**. 출력 길이가
달라(평균 약 400 vs 680토큰) E2E는 비교하지 않는다.

| 동시 요청 수 (FP16) | 1 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|
| T4×1 E2E p50 | 22 s | 28 s | 34 s | 61 s | 94 s |
| T4×1 출력 tok/s | 28 | 75 | 124 | 156 | 195 |
| T4×2 E2E p50 | 12 s | 16 s | 19 s | 33 s | 54 s |
| T4×2 출력 tok/s | 53 | 132 | 217 | 281 | 357 |

관찰
- **동시 처리의 효과**: T4 1장에서 요청 하나는 28 tok/s지만 32개를 묶으면 195 tok/s(7배). 대신 토큰당 시간이
  4배로 늘어 한 건이 94초 걸린다. 진료기록 한 건을 30초 안에 받는 것을 기준으로 하면 T4 1장은 동시 4건,
  T4 2장은 동시 8~16건이 적정 → API의 동시 처리 상한(`MAX_INFLIGHT`)을 이 표로 정한다.
- **Tensor Parallel(GPU 2장)**: 3B 모델인데도 토큰당 시간이 절반(34→17 ms), 최대 처리량 1.8배. 가중치를 나눠
  GPU마다 남는 메모리가 커져 KV 캐시가 3배(동시 처리 여력 21→66건)가 된 것이 크다.
- **4bit 양자화(AWQ)**: 가중치 3배 축소, 동시 1건에서는 토큰당 2.3배 빠르다(디코딩은 가중치를 읽는 속도가
  병목이라 읽을 양이 줄면 빨라진다). 하지만 동시 32건에서는 차이가 6%로 줄어든다(134 vs 143 ms) — 많이 묶으면
  계산이 병목이 되고, T4에는 4bit 행렬곱 전용 하드웨어가 없어 압축을 푸는 비용이 붙는다.
  → **4bit는 지연 시간·메모리용이지 T4의 최대 처리량용이 아니다.**
- **JSON 스키마 강제 비용**: 토큰당 0~4% 느려질 뿐이다. 출력이 섹션 제목 없이 짧아져(평균 595 vs 681토큰)
  한 건 완성 시간(E2E)은 오히려 줄었다.

측정 방법 메모 (같은 실수를 하지 않도록)
- vLLM 0.32에는 bitsandbytes 양자화가 빠졌다. `int8_per_channel_weight_only`는 일반 모델에서 로그에
  "Quantizing 0 layers"가 찍히며 **아무 층도 양자화하지 않는다**(메모리 5.79 GB 그대로). 이 설정으로 돌린
  품질 평가는 사실상 FP16 재실행이라, 같은 설정을 두 번 돌린 편차(ROUGE-1 55.5 vs 55.1)를 확인하는 용도로만 쓴다.
- **1차 측정은 실제보다 좋게 나왔다.** 단계마다 같은 대화를 다시 보내 prefix cache가 입력 처리를 건너뛰었다
  (로그상 적중률 50~70%). 단계마다 새 대화를 쓰도록 고쳐 재측정하니, T4×1 동시 32건에서 첫 토큰까지 시간(TTFT p50)이
  0.65 → 3.7 s, 처리량이 220 → 195 tok/s로 바뀌었다. 실제 서비스에서는 대화가 매번 다르므로 2차 값이 맞다.
- `vllm serve`는 모델의 `generation_config.json`(repetition_penalty 1.05)을 기본값으로 쓴다 →
  `--generation-config vllm`으로 끄고 품질 평가와 같은 생성 설정을 쓴다.

## API 서버 — `service/`

모델 서버와는 OpenAI 호환 API로만 통신해서, 같은 코드로 vLLM(GPU)과 llama.cpp(CPU)를 환경변수만 바꿔 쓴다.

| 엔드포인트 | 내용 |
|---|---|
| `POST /v1/notes` | 대화 → 4구역 JSON 진료기록. 스키마 강제 + pydantic 검증, 출력이 잘려 JSON이 깨지면 반복 벌점을 올려 1회 재시도 |
| `POST /v1/notes/stream` | 같은 생성을 SSE로 토큰 단위 스트리밍, 마지막에 검증 결과(`done`/`error`) 이벤트. 사용자가 연결을 끊으면 모델 서버 생성도 중단 |
| `GET /health` | 모델 서버 연결 확인 |
| `GET /metrics` | 요청·실패·재시도·거절 수, 처리 중 요청 수, 지연 p50/p95 |

- **과부하 보호**: 동시 처리 상한(`MAX_INFLIGHT`)을 넘는 요청은 API 앞에서 기다리고, `QUEUE_TIMEOUT_S` 안에
  자리가 안 나면 503 + `Retry-After`로 바로 거절한다. 모델 서버 대기열이 끝없이 길어져 모든 요청이 느려지는 것을 막는다.
- **입력 검증**: 너무 짧거나(422) 문맥 길이를 넘는 대화(413)는 모델 서버까지 보내지 않는다.
- **근거 표시(`review`)**: 응답마다 대화에 근거가 없는 나이·수치·검사 이름을 표시하고 `needs_review`를 켠다
  (`src/faithfulness.py`와 같은 기준). 생성을 막지는 않고 의료진이 확인할 곳을 짚어 준다.
- **실제 HTTP 경로 확인**: uvicorn API + 가짜 모델 서버(응답 0.5초)로 `loadtest.py`를 돌려, 동시 처리 상한 2에서
  모델 서버가 받은 최대 동시 요청이 2였고, 동시 사용자 8명일 때 대기 한도(1.2초)를 넘긴 4건이 503으로 거절됨을 확인.
- **테스트** (`tests/test_service.py`, 8개): 실제 OpenAI 클라이언트 코드 경로를 그대로 타고, 네트워크만 가짜 모델
  서버로 바꿔 정상 생성, 잘린 JSON 재시도, 두 번 실패 시 502, 모델 서버 오류, 입력 검증, 스트리밍, health를 확인한다.
- **배포**: `service/Dockerfile`(API 이미지, 모델 미포함), `docker-compose.yml`
  (`--profile cpu` = llama.cpp + GGUF, `--profile gpu` = vLLM).
- **부하 테스트**: `service/loadtest.py` — API 계층(검증·재시도·대기열)까지 포함한 실제 서비스 경로를 동시 사용자 수별로 잰다.

## 한계

- **영어 데이터만 사용.** 공개된 "진료 대화 → 전체 진료기록" 데이터는 모두 영어이고, 한국어 데이터는 찾지 못했다.
- **대화는 역할극.** ACI-BENCH는 의사와 연기자가 진료를 연기한 대화라 실제 진료보다 정돈되어 있다.
- **데이터가 작다.** 사람이 작성한 학습 데이터는 67건이다. 수천 건 규모 공개 데이터(MedSynth, NoteChat 등)는
  모두 LLM이 만든 합성 데이터라 기록 스타일이 다르다.
- **모델 라이선스.** Qwen2.5-3B는 Apache 2.0이 아닌 Qwen Research License(비상업)다. 상업 서비스라면
  Apache 2.0 모델(Qwen2.5-7B, Qwen3 계열 등)로 바꿔야 한다.
- **ROUGE는 단어 겹침만 본다.** 사실 오류나 환각을 직접 측정하지 못해, 대표 사례를 사람이 확인한다.
